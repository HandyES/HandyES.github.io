一、Function Calling协议总览（理论 5min）

1.1 从Prompt描述到协议化调用

第04课中，我们用Constrained Decoding让模型输出JSON格式的工具调用意图。这是”Prompt层工具调用”——模型知道工具存在（通过System Prompt描述），但API层面没有原生的工具调用支持。

Function Calling（函数调用） 是LLM API的原生能力：模型不仅能理解工具描述，还能在API响应中直接生成结构化的工具调用请求，无需应用层解析自由文本。

核心差异：Function Calling把工具调用的”理解”和”生成”从应用层下沉到模型层。模型经过专门训练，能理解JSON Schema描述的工具语义，并在响应中以结构化格式输出调用请求。

1.2.1 OpenAI实现要点

OpenAI是Function Calling的行业标杆，大多数其他厂商（包括DeepSeek）采用兼容其格式的方式。

tool_choice的三种模式：

  • "auto"：模型自主决定是否调用工具（默认）
  • "required"：模型必须调用至少一个工具

二、JSON Schema工具描述（理论 4min）

2.1 JSON Schema类型系统

Function Calling的工具描述基于JSON Schema（Draft 2020-12）。理解类型系统是设计高质量工具的前提。

JSON Schema核心类型与约束：

类型 关键约束关键字 工具设计用途
string minLength, maxLength, pattern, enum, format 限制查询长度、格式化日期、枚举排序方式
integer/number minimum, maximum, multipleOf 限制结果数量、年份范围
boolean — 开关参数（是否包含预印本）
array items, minItems, maxItems, uniqueItems 多值参数（多个关键词、多个字段）
object properties, required, additionalProperties 嵌套结构（日期范围、地址）
null — 可选参数的空值表示

2.2 枚举约束的工程价值

枚举（enum）是控制模型行为的最有效约束之一。它将模型的”自由生成”降维为”有限选择”，极大降低参数幻觉率。

工程经验：当一个参数的合法取值是有限集合时，永远用枚举。测试数据显示，枚举约束可将参数错误率降低80%以上。

2.3 递归Schema

某些工具参数具有递归结构——例如引用网络分析中的”递归展开”参数：

$ref 用于递归引用，# 表示Schema根节点。递归Schema的实际深度通常需要限制（如上例中depth最大为3），避免无限递归导致模型生成超长参数。

2.4 Strict模式的Schema约束

OpenAI的Strict模式（strict: true）要求Schema遵循额外约束 $TRAE_REF：

约束 说明 原因
additionalProperties: false 必须显式关闭额外属性 确保模型不生成未定义的字段
所有字段在required中或有default 所有属性必须明确可选性 模型需要知道哪些字段必须生成
anyOf替代oneOf 使用anyOf而非oneOf oneOf的互斥验证在模型生成时不可靠
无$ref到外部文件 仅支持Schema内部$ref 模型推理时无法访问外部文件

必须掌握：JSON Schema类型系统是Function Calling的基石。设计工具时，每个参数都应思考：类型是否正确？约束是否充分？枚举是否完备？描述是否清晰？

三、并行工具调用与依赖图（理论 3min）

3.1 并行调用的场景

当用户提问”对比Smith和Johnson在Agentic RL领域的贡献”时，Agent需要同时搜索两位作者的论文。串行调用需要两轮LLM交互（先搜Smith，再搜Johnson），并行调用只需一轮。

OpenAI和Claude都原生支持在单次响应中返回多个工具调用 $TRAE_REF。应用层需要并行执行这些调用，聚合结果后一次性返回给模型。

3.2 依赖图分析

并非所有工具调用都能并行。有些调用存在数据依赖——后一个调用的参数依赖前一个调用的结果。

依赖图建模：将每个工具调用视为图中的节点，数据依赖视为有向边。若图是无环的（DAG），则可通过拓扑排序确定执行层次。

3.3 拓扑排序的复杂度分析

设n个工具调用，m条依赖边：

操作 时间复杂度 说明
建图 O(m) 遍历所有依赖关系
拓扑排序 O(n + m) 每个节点和边访问一次
分层并行执行 O(L × T_max) L=层数，T_max=单层最大执行时间

关键优化：并行执行的总延迟取决于最长路径（关键路径），而非调用总数。将独立调用分组到同一层，可将延迟从O(n × T)降低到O(L × T_max)。

项目线关联：研究助手Agent的analyze_citation_network工具内部需要多步调用（先获取论文详情，再获取引用列表，最后分析引用网络）。本课的调度器将作为该工具的内部执行引擎。

必须掌握：并行调用的依赖图拓扑排序是本课核心知识点。理解DAG建模、分层执行、关键路径分析，是设计高效Agent工具系统的关键。

四、工具调用错误处理（理论 3min）

4.1 错误分类与处理策略

工具调用在生产环境中会遭遇多种错误。设计健壮的错误处理机制是Agent可靠性的关键。

错误类型 典型场景 处理策略 重试是否有效
网络超时 API调用超时 指数退避重试 ✅ 有效
速率限制 429 Too Many Requests 退避后重试 ✅ 有效
参数错误 模型生成非法参数 修正参数后重试 ⚠️ 需LLM重新生成
工具不存在 模型幻觉了不存在的工具 拒绝并提示可用工具 ❌ 无效
权限不足 用户无访问权限 降级或请求授权 ❌ 无效
数据不存在 搜索结果为空 返回空结果，让LLM决定下一步 ❌ 无效
服务不可用 5xx服务器错误 故障转移到备用工具 ⚠️ 视情况

5.4 架构决策练习

场景：你正在为研究助手Agent设计工具体系，面临以下约束：

  • 预算：每月$500 API费用
  • 并发：高峰期50个用户同时使用
  • 延迟要求：单次工具调用P99 < 5秒
  • 工具数量：当前4个，未来需扩展到15个
  • 需支持OpenAI和Claude双后端

问题：

  1. 工具定义是放System Prompt还是tools参数？为什么？
  2. 15个工具是否全部注册？如何管理工具的按需加载？
  3. 并行调用的max_workers设为多少？考虑什么因素？
  4. 超时时间设为多少？重试策略如何配置？
  5. 双后端如何设计适配层？Token开销如何控制？

参考思路：

  1. 用tools参数（Function Calling原生支持），而非System Prompt。原因：①API保证格式正确性；②支持strict模式；③Token开销更低（工具定义不占用context window的注意力）。
  2. 不全注册。采用第04课的Skills按需加载机制——根据用户意图先加载3-5个相关工具，避免工具过多导致选择准确率下降（Gemini在10+工具时准确率从95-98%降至90-94%） $TRAE_REF。
  3. max_workers设为4-8。考虑因素：①API速率限制；②数据库连接池；③CPU/GPU资源。50并发用户 × 每用户最多4并行 = 200并发工具调用，需配合队列管理。
  4. 超时5秒（满足P99要求），重试3次，指数退避（1s/2s/4s），总最大延迟5+4=9秒（含重试）。
  5. 用5.1节的ToolCallAdapter抽象层。Token控制：优先用Gemini（180-350 tokens vs OpenAI 200-400 vs Claude 300-500），但Claude在详细描述时准确率更高——可用Claude做复杂任务，Gemini做简单任务 $TRAE_REF。

九、参考答案

题1 答案

additionalProperties: false 禁止模型生成Schema中未定义的额外属性，确保输出严格匹配预期结构。required 明确哪些字段必须出现。

Strict模式要求两者同时存在的原因：required让模型知道哪些字段必须生成（避免遗漏关键参数），additionalProperties: false让模型知道不能生成额外字段（避免幻觉出不存在参数）。两者结合将模型的输出空间从”任意JSON”约束为”精确匹配Schema的JSON”，将参数格式错误率从2-5%降至接近0 $TRAE_REF。

常见错误模式：只设required不设additionalProperties: false——模型可能生成{"query": "...", "max_results": 10, "language": "zh"}，其中language是幻觉出的额外字段，可能导致工具执行时出现意外行为。

题2 答案

差异 OpenAI Anthropic Claude 优劣分析
响应格式 tool_calls独立字段 tool_use内容块（与text交错） Claude的优势：文本和工具调用可交错，模型可以先解释再调用；OpenAI的优势：解析更简单，tool_calls是独立字段
参数类型 JSON字符串（需json.loads()） Python dict（直接可用） Claude更方便，无需额外解析；OpenAI需处理JSON解析失败的边界情况
结果返回 role: "tool" + tool_call_id tool_result内容块 + tool_use_id Claude的方式更显式，多轮工具对话更清晰；OpenAI更简洁

题3 答案

从EXECUTING出发的转换路径：

共4条到达终态的路径：

  1. EXECUTING → SUCCEEDED（正常完成）
  2. EXECUTING → RETRYING → EXECUTING → … → SUCCEEDED（重试后成功）
  3. EXECUTING → RETRYING → FAILED → FALLBACK → DEGRADED（重试耗尽+降级成功）
  4. EXECUTING → FAILED → FALLBACK → FAILED（致命错误+无降级）

常见错误模式：忘记FAILED → FALLBACK路径，导致错误后直接返回失败，未尝试降级方案。

题5 答案

(a) 8个工具 × 80 tokens = 640 tokens/次调用。月度开销：640 × 100,000 = 64,000,000 tokens = 64M tokens。费用：64M × $2.50/M = $160/月

(b) Skills按需加载后：3个工具 × 80 tokens = 240 tokens/次。月度开销：240 × 100,000 = 24M tokens。费用：24M × $2.50/M = $60/月。节省：$160 - $60 = $100/月（节省62.5%）

(c) Gemini的Token开销更低（180-350 tokens per 3-5 tools vs OpenAI 200-400） $TRAE_REF。8个工具在Gemini上约560 tokens/次。月度：56M tokens × $2.00/M = $112/月。相比OpenAI节省$48/月（30%）。

常见错误模式：只计算工具定义的Token开销，忽略工具调用响应（30-80 tokens/次）和结果返回的Token开销。实际总开销应乘以1.2-1.5的系数。
