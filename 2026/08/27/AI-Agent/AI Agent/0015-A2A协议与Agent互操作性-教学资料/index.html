一、从框架内到跨组织：为什么需要A2A（协议原理 Part 1）

1.1 第14课的边界：三重假设失效

回看第14课的Supervisor模式——Orchestrator调用w.execute(text, artifact)，Retriever/Analyst/Reviewer是同一个Python进程里的对象。这带来了三个免费赠送的奢侈假设：

进程内假设 跨组织现实 后果
共享内存：工件artifact是一张字典，谁都能读写 网络分隔，各有各的上下文与数据 需要消息协议+状态同步机制（第14课的共享黑板失效）
统一时钟：调用是同步阻塞的，execute返回即完成 网络分区、部分失败、延迟不可控 需要异步任务模型+状态轮询/推送
天然信任：所有代码都是你写或你审计过的 对端是第三方黑盒（“opaque”） 需要身份认证+能力验证+授权

第14课预告的原话：“分布式系统的全部经典难题（部分失败、身份、不可信协作），将在Agent互操作的名义下重新登场。”——A2A协议正是对这三重失效的系统性回答。

1.2 A2A是什么：定位与分层

A2A（Agent2Agent）协议是一个开放标准，由Google于2025年4月发起、后捐赠给Linux基金会治理，目标是让不同框架、不同厂商、不同组织构建的Agent能够相互发现能力、协商交互模式、安全协作完成任务——而不暴露内部状态（这一点与MCP的"工具封装"哲学一脉相承：协作靠消息，不靠共享内存）。

用一张分层图定位它与已学协议的关系：

**行业共识的分工口诀：MCP连接Agent与工具，A2A连接Agent与Agent。**两者不是竞争而是互补——研究助手会用MCP调用文献检索工具（第11课已实现），同时用A2A把"专利深度调研"这类任务委派给外部专业Agent。

一个自然的问题：**Agent和工具的边界在哪？**判据是自主性：工具是无状态的函数调用（输入→输出，立即返回），Agent是有状态的推理循环（接收任务→规划→执行→可能要求补充信息→交付）。当外部服务开始"需要多轮交互才能完成你的请求"时，它就该用A2A而不是MCP来暴露。

二、Agent Card：能力的机器可读描述（协议原理 Part 2）

2.1 发现机制：well-known URI

跨组织协作的第一步是"找到对方并知道它能干什么"。A2A沿用Web的成熟惯例——well-known URI（与MCP的/.well-known/mcp、HTTPS证书的/.well-known/acme-challenge同族）：

Agent把自己的能力描述（Agent Card）挂在这个约定路径上，任何客户端无需注册、无需账号即可读取——这就是"路由知识分布在描述里"（第14课Swarm路由思想）的跨组织标准化版。

2.2 JSON-LD语义模型：为什么不只是JSON【必须掌握】

Agent Card的设计渊源是JSON-LD（JSON Linked Data）——W3C的语义网标准。理解这个渊源，才能理解Agent Card为什么长这样：

JSON-LD的三个核心思想及其对Agent互操作的意义：

JSON-LD机制 含义 对Agent互操作的意义
@context 把短键名（如skills）锚定到全局唯一URI词汇表 不同厂商的Agent对"skill"一词有同一机器可读定义——语义对齐的基础设施
RDF三元组 一切数据都是（主体，谓词，客体），如(PatentAgent, hasSkill, patent-search) Agent能力可被推理引擎做逻辑查询：“找所有具备patent-search技能且支持流式的Agent”
Linked Data 值可以是外部URL，顺着链接可获取更多语义 Agent Card中的securitySchemes可引用组织级安全策略文档，形成信任链

v1.0的实践立场：随着a2a.proto升格为规范唯一事实源，Agent Card的主体结构以proto映射的纯JSON（camelCase字段）为准；JSON-LD作为语义模型的设计思想保留在@context扩展能力与skills标签体系中。架构师需要记住的结论：Agent Card的本质是一份机器可读的能力契约——它让"找一个会做X的Agent"从搜索引擎问题（不可靠）变成结构化查询问题（可验证）。

2.3 Agent Card v1.0结构解析【必须掌握】

一份v1.0风格的Agent Card（注释标注关键设计）：

五个v1.0关键变化（相对0.x，全部影响你的实现）：

  1. supportedInterfaces[]取代url+preferredTransport+additionalInterfaces：每个接口独立声明url/protocolBinding/protocolVersion三要素——同一Agent可以同时暴露JSON-RPC和gRPC两种绑定，客户端按自己的技术栈选择。
  2. protocolVersion从卡顶层下沉到每个接口：支持平滑升级——一个端点可以先升级到1.1，另一个仍停留1.0。
  3. capabilities.extendedAgentCard取代顶层supportsAuthenticatedExtendedCard：认证后可获取的"扩展卡"（含非公开技能）声明归入能力对象。
  4. skills[].tags成为必填：tags驱动skill级匹配——路由器（客户端的委派决策）把任务特征与skills的tags做匹配，"范围每个skill到单一任务边界"是官方最佳实践。
  5. signatures[]数组：Signed Agent Cards的载体（下节）。

skill划分的工程直觉：skill是发现的单元，粒度=任务边界。研究助手检索层的三个子技能（文献检索/专利检索/内网库检索）应声明为三个skill，而不是一个"检索"大杂烩——粒度过粗导致误匹配，过细导致发现效率下降。

2.4 Signed Agent Cards：防篡改的信任锚【应当理解】

威胁场景：Agent Card挂在公开URL上，任何客户端可读——同样意味着中间人可以篡改它。攻击者把Card里的接口地址替换为自己的服务器、把安全要求从OAuth降级为明文、把能力声明夸大——客户端的委派请求就被引向恶意Agent（典型的降级攻击+请求劫持）。

v1.0的解法是Signed Agent Cards：

架构师要点：签名验证在交互之前完成——这是"组织边界外的信任建立"（trust before interaction across organizational boundaries）。第04课的Prompt注入防御（输入消毒）防的是内容层攻击；Signed Card防的是元数据层攻击（能力声明本身的伪造）——两道防线缺一不可：Card是真的，不代表它返回的内容是无害的。

三、Task生命周期：跨组织的任务状态机（协议原理 Part 3）

3.1 Message vs Task：两种响应模式

客户端发消息给Agent后，Agent有两种根本不同的响应方式：

无状态Message 有状态Task
适用 琐碎交互、能力/范围协商（“你能处理X吗？”） 长时间、需跟踪、可能中断的工作
返回 立即的Message Task对象（随后演进）
典型 直接包装LLM调用的简单问答 “调研某领域专利全景”（分钟级+多轮补充）

按两种模式的使用比例，Agent分三种形态：Message-only（永远返回Message）、Task-generating（一切皆Task，简单回答也建模为completed任务）、Hybrid（先用Message协商范围，确认后转Task跟踪执行——官方推荐的复杂Agent形态）。

3.2 Task状态机：完整状态转换图【必须掌握】

v1.0的八个状态（SCREAMING_SNAKE_CASE）与转换关系：

状态语义与转换规则（协议规定，考试级掌握）：

状态 语义 谁触发 出口
SUBMITTED 任务已被受理，尚未开始执行 服务端创建 →WORKING / →REJECTED / →FAILED
WORKING 执行中 服务端 →COMPLETED / →FAILED / →INPUT_REQUIRED / →AUTH_REQUIRED / →CANCELED
INPUT_REQUIRED 中断态：信息不足，等待客户端补充（如缺专利分类号） 服务端 客户端在同一taskId上追加Message → WORKING
AUTH_REQUIRED 中断态：需要完成认证/授权（如token过期） 服务端 认证后重试 → WORKING
COMPLETED 终态：成功，artifacts已就绪 服务端 无（不可重启）
FAILED 终态：执行失败（错误信息在Task的message里） 服务端 无
CANCELED 终态：客户端CancelTask成功 客户端请求 无
REJECTED 终态：服务端受理后拒绝（能力不匹配/非法请求） 服务端 无

与第14课Handoff状态机的对比（回收伏笔）：第14课的Handoff状态机（IDLE→ACTIVE→DONE）管理的是进程内控制权转移，状态是私有的实现细节；A2A Task状态机管理的是跨组织工作契约，状态是公开的协议承诺——客户端依赖这些状态做超时、重试、降级决策。额外的两个中断态（INPUT_REQUIRED/AUTH_REQUIRED）正是"不可信边界"的产物：HITL（第12课interrupt）的跨组织版。

3.3 Task不可变性与精炼模式【应当理解】

不可变性原则：Task一旦到达终态（COMPLETED/CANCELED/REJECTED/FAILED），不可重启。后续交互（如"把结果改成红色帆船"）必须在同一contextId下创建新Task，并用referenceTaskIds引用原任务。

三个配套机制：

  • contextId：逻辑上分组多个Task和Message——服务端用它管理内部LLM会话状态（跨任务的对话连续性）。同一context下的Task可并行（订机票→并行订酒店+订雪橇车）。
  • Artifact版本追踪归客户端：服务端对同一工件的精炼版本保持一致的artifact-name但分配新artifactId；版本历史由客户端维护（客户端才是"什么算可接受结果"的裁决者）——这个设计决策把责任交给信息优势方。
  • ID简化：v1.0把复合ID（tasks/{taskId}/pushNotificationConfigs/{configId}）全部简化为简单UUID+分离字段——“ID直接映射数据库主键”，实现复杂度骤降。

为什么不可变？ 回忆第12课的Checkpoint回放：不可变对象给了编排器可靠的因果追踪（每个输入对应哪个输出单元），trace与审计（第05课操作审计日志）才有干净的锚点。可重启的Task是分布式系统里最危险的模糊状态——"这个任务到底完成了没有"在部分失败场景下无法回答。

三个工程细节值得注意：①流事件重设计——v0.3的kind判别字段与final布尔值被移除，事件类型由JSON成员名（statusUpdate/artifactUpdate包装对象）判别，流的关闭（协议绑定特定机制）即终止指示；②ListTasks的可见性规则——服务端"必须只返回该调用者可见的任务"（多租户安全，见第四节）；③推送通知负载改用StreamResponse格式，与流式API统一。

与第12课异步架构的衔接：A2A的"轮询（GetTask）/流式（SendStreamingMessage）/推送（PushNotificationConfig）"三通道，就是第12课"异步Agent与事件驱动架构"在协议层的标准化——概念完全同构，只是从框架API升级为跨组织契约。

四、安全机制：不可信边界的信任建立（协议原理 Part 4）

4.1 三层安全栈

4.2 OAuth 2.0现代化：对齐Security BCP

v1.0把OAuth支持对齐到OAuth 2.0 Security Best Current Practice：

变化 原因 Agent场景含义
移除 Implicit流 token暴露在浏览器历史/日志 Agent无浏览器，本就不该用
移除 Password流 凭据直传风险 服务Agent绝不该存第三方密码
新增 Device Code流（RFC 8628） 无头环境认证 CLI工具/IoT/无人值守Agent：verification_uri+user_code模式，人机分离认证
新增 pkce_required字段 防授权码拦截攻击 授权码流强化：公开客户端必须PKCE

凭据带外获取原则：A2A协议本身不传输凭据获取过程——OAuth流程/密钥分发在协议外（out-of-band）完成，协议只消费已获得的token。这与Agent Card的securitySchemes声明（与OpenAPI Specification对齐）配合：认证要求在Card里声明，凭据在协议外获取，请求在协议内验证。

4.3 多租户与任务可见性

v1.0原生多租户：请求消息携带tenant字段（可从AgentInterface继承默认值），单个端点安全托管多个Agent——对SaaS化Agent服务（一个域名后托管数百个客户的Agent）是关键能力。配套的可见性规则：GetTask/ListTasks只返回该认证调用者可见的任务——防跨租户信息泄露的协议级保证。

五、互操作性挑战：语义对齐与能力协商（协议原理 Part 5）

协议标准化了"怎么说话"，但两个根本难题仍然存在——这是本课理论顶点。

5.1 语义对齐问题

同一张Agent Card，双方理解一致吗？三个层次的语义鸿沟：

工程对策组合：skills的examples字段展示典型请求-交付对（缩小语义层鸿沟）、defaultInputModes/OutputModes声明交付形态、Hybrid形态的Message预协商（先问"你能做X并30分钟内交付吗"再委派Task）。语义对齐没有银弹——协议给了机器可读的框架，剩余的对齐成本靠交互设计消化。

5.2 能力协商的形式化：从匹配到博弈【必须掌握】

"能力协商"听起来礼貌，本质是利益博弈：服务端Agent希望接到更多任务（夸大能力有利可图），客户端Agent希望任务成功（误信夸大代价高昂）。用博弈论严格分析。

博弈的三要素：参与人N={S（服务端）, C（客户端）}，策略空间Sᵢ，效用uᵢ。

模型一：一次性能力声明博弈

设支付矩阵（数值可自定，结构是关键）：

求纯策略纳什均衡（回忆定义：策略组合σ*，任一参与人单方面偏离无法获益）：

  • (H, D)：S偏离到O可得12>8 → 非均衡
  • (O, D)：C偏离到R可得0>-5 → 非均衡
  • (H, R)：C偏离到D可得10>0 → 非均衡
  • (O, R)：C给定O，R得0>D得-5，无偏离动机 ✓；S给定R，O与H都得0，无严格偏离动机 ✓

结论：唯一的（弱）纳什均衡是（夸大，拒绝）——市场崩溃。这正是Akerlof"柠檬市场"的Agent版：不对称信息摧毁互操作市场。一次性、匿名、无验证的开放Agent网络中，理性参与者互相不信任是均衡行为而非道德问题。

六、ANP：去中心化的另一条路线（知晓即可）

A2A走的是企业联盟中心化路线：域名+DNS+HTTP+OAuth+PKI——信任锚是CA与授权服务器。另一条开放网络去中心化路线是ANP（Agent Network Protocol）——开源社区项目（W3C社区组技术报告），承诺开放中立、永不商业化。

ANP三层架构：

v1.1协议族：ANP-07（Agent Description，能力描述与发布）、ANP-08（Agent Discovery，主动.well-known发现+被动注册到搜索智能体）、ANP-09（端到端即时消息：私聊/群聊/E2EE/附件/联邦语义）。

身份机制对比（ANP的DID认证）：请求方用自己的私钥对挑战字符串签名，签名附在HTTP Authorization头——不依赖任何CA/授权服务器，自主权身份。Agent之间像"网站爬虫顺着链接发现页面"一样通过Linked Data相互发现——无需中心注册地自组织组网。

九、参考答案

A1

四个终态：COMPLETED/FAILED/CANCELED/REJECTED——均不可逆。两个中断态：INPUT_REQUIRED（等客户端补充信息，客户端在同一taskId上追加Message后回WORKING）、AUTH_REQUIRED（等带外认证，重试后回WORKING）。客户端发起的转换：CANCELED（CancelTask请求）；INPUT_REQUIRED/AUTH_REQUIRED的恢复也由客户端的后续消息驱动。INPUT_REQUIRED不能是终态：因为任务的目标尚未失败也未完成，只是暂停等待信息——若设为终态，“补一个分类号"就得重建整个任务（丢失已有进度与服务端已做的推理），交互成本不可接受。终态的本质语义是"该工作单元已产生最终裁决（成功/失败/取消/拒绝），因果链已闭合”。

A2

维度 MCP A2A ANP
连接对象 Agent↔工具/数据 Agent↔Agent（跨组织） Agent↔Agent（开放网络）
信任模型 平台内信任+OAuth 2.1 DNS+PKI+OAuth+mTLS（企业联盟） W3C DID自主身份（去中心化）
发现机制 server/discover+Mcp-Method头路由 Agent Card（/.well-known/agent-card.json） ANP-07描述文档+Linked Data爬取发现
状态模型 v2.0无状态核心（显式handle） 有状态Task生命周期（8状态） 即时消息+联邦语义

研究助手场景：MCP→调用文献检索工具（第11课已实现）；A2A→把专利深度调研委派给外部供应商Agent（本课实战）；ANP→观察开放Agent网络生态的实验性接入（知晓即可）。

A3

  • (a) 错。v1.0把protocolVersion从Card顶层下沉到supportedInterfaces[]的每个AgentInterface对象（url/protocolBinding/protocolVersion三要素）——支持接口级独立升级。
  • (b) 对。v1.0移除kind判别字段，流事件由JSON成员名判别（statusUpdate/artifactUpdate包装对象），final布尔字段同时移除，流的关闭由协议绑定特定机制指示终止。
  • © 错。Task不可变性原则：终态Task不可重启。精炼请求必须在同一contextId下创建新Task，并用referenceTaskIds引用原任务。
  • (d) 错。v1.0中skills[].tags为必填——tags驱动skill级匹配，是路由器匹配任务的依据。

B1

验证机制改变博弈：夸大被发现的概率p=0.6。发现后拉黑，故夸大的后续收益为0；未发现（概率0.4）时得12。

40 ≫ 4.8，诚实成为严格占优策略——激励相容达成。验证机制除了改变支付结构，还改变了：①信息结构——“夸大vs交付"从不可观测变成可观测（可验证性是声誉的前提）；②博弈的重复性——拉黑机制把一次性博弈有效转成"最后通牒式重复博弈”，δ的意义从主观耐心变成制度化的退出机制。这正是5.2节结论的例证：A2A用Task状态机+可验证artifacts+任务历史设计支付矩阵，使诚实成为均衡。

B2

角度 不可变（A2A选择） 可重启
因果追踪与审计 每个Task=一个清晰的输入→输出单元，trace/artifact映射干净（呼应第12课Checkpoint回放的价值） COMPLETED任务"又活了"，审计日志中同一taskId对应多个交付版本，因果链模糊

深层理由：分布式系统中"已完成但可能被撤销"是最危险的模糊状态（类比数据库的幻读）。A2A用"不可变+引用"（新建Task引用旧Task）替代"可变+重入"——这正是不可变数据结构在并发编程中优势的协议级复现。代价是任务对象数量增长，由ListTasks游标分页（v1.0新增）缓解。

B3

攻击发生在内容/交付层（服务端运行时被入侵→数据伪造），而Signed Agent Cards保护的是元数据层（Card声明本身的完整性与来源）——签名保证"这确实是供应商的Agent Card、内容未被篡改"，但不保证"该Agent运行时行为诚实"。防御应放在研究助手侧的交付物验证：①Proposer-Reviewer模式（第14课）——独立审核Agent对返回的专利数据做核验（编号存在性/引用数合理性/交叉源比对）；②多源交叉验证（专利数据与arXiv/内网库比对）；③评估融入——把外部Agent交付质量纳入第10课评估体系（faithfulness指标）。安全是分层的：签名防元数据伪造，验证机制防内容欺骗，两者互补。

C1（参考方案）

①Agent Card：skills按任务边界划分——lit-review（主题综述：tags=[research, survey, writing]）与citation-verify（引文核验：tags=[citation, verify, fact-check]）。不设"超级检索"大杂烩skill（匹配噪声）。supportedInterfaces声明JSONRPC绑定+protocolVersion；capabilities.extendedAgentCard=true（认证后暴露企业客户专属技能）。

②状态触发规则：INPUT_REQUIRED——主题过宽（如"AI综述"）时要求限定范围与时间窗；引用列表缺失时要求提供。REJECTED——主题超出知识域（非科研领域）、请求含注入攻击模式（第04课消毒层拦截）。WORKING→FAILED——内部RAG流水线异常，错误信息入Task message。

③多租户：v1.0原生tenant字段——每个客户组织一个tenant ID；OAuth token与tenant绑定；Task存储按tenant分片（DB行级隔离或schema隔离）；GetTask/ListTasks强制tenant过滤（协议规定"只返回调用者可见的任务"）。计费与配额按tenant维度。

④签名与密钥管理：发布方持有Ed25519私钥（HSM/KMS托管，运维不可导出）；Card变更走CI流水线：新版本→RFC 8785规范化→KMS签名→signatures[]更新→发布；公钥通过带外渠道（客户组织的密钥分发/JWK endpoint）分发；定期轮换（双签名过渡期）。验签失败策略：拒绝委派+告警（而非降级继续）。

评分要点（对应大纲6维度）：技能粒度合理（选型）；状态规则覆盖中断与拒绝（完整性）；租户隔离方案（安全）；密钥管理流程完整（安全+可扩展）。

C2（参考方案）

①消息协议统一：定义内部标准信封（第14课msg_id/trace_id/hop_count三件套保留），进程内子Agent直接消费；外部Agent经A2A适配器做双向转换——本地信封→SendMessage的message.parts[0].data（携带结构化字段），Task的statusUpdate/artifacts→本地信封。关键：contextId与本地trace_id的映射表（委派时建立，恢复时反查）。

②INPUT_REQUIRED流转：A2A客户端适配器收到INPUT_REQUIRED→向LangGraph图发interrupt（第12课HITL机制）→图暂停，human节点构造问题呈现给用户→用户回答→Command(resume=答案)恢复→适配器在同一taskId上SendMessage补充信息。超时未答（如30min）→CancelTask+降级。

③循环委派检测：wait-for图映射——Orchestrator等待外部Agent=wait边（标注taskId）；外部Agent又把任务委派回研究助手（或链式委派形成环）时，检测方法：在委派消息的data part中携带delegation_chain（累积taskId列表），收到委派请求时先查链上是否已有本Agent的taskId——有则拒绝（REJECTED）并返回链证据（这比wait-for图更轻量，本质是把hop_count从单跳推广到全链）；跨组织无全局视图，无法做第14课的三色DFS中心化检测，只能靠链上自检（分布式系统经典权衡：中心化检测vs链式自检）。

④容错分层：

  • 超时：连接超时3s（快速失败）/任务超时按skill定（检索类120s，综述类1800s+轮询间隔自适应退避）；
  • 重试：网络层错误（5xx/超时）幂等重试2次（SendMessage需幂等键防重复建Task）；协议层FAILED不重试（业务失败重试无意义），换降级源；
  • 降级：三级fallback——外部A2A专利源失败→MCP内网检索工具（能力降级但可用）→返回部分结果+明确标注缺口（比假完整好，呼应第14课MAST"工具输出未验证"教训）；
  • 熔断：某外部源近5分钟失败率>50%→熔断10min，直接走降级（防止雪崩）。

常见错误模式：①把外部Agent当本地函数调用（同步阻塞无超时）——研究助手整体被外部故障拖死；②INPUT_REQUIRED无人应答导致Task永久挂起（必须配超时+取消）；③委派消息不带结构化元数据（trace断链，失败无法归因——第14课TraceElephant教训）；④忽略签名验证（元数据层裸奔）；⑤重试不带幂等键（重复计费+重复交付）。
