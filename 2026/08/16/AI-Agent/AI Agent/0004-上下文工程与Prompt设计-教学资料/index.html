本课导读

第03课我们设计了Agent的推理循环架构——ReAct的Thought-Action-Observation三元组、Plan-and-Execute的DAG分解、Reflexion的反思闭环，并为研究助手Agent选定了Reflexion+Plan-Execute嵌套架构。但一个关键问题悬而未决：Agent的推理质量，很大程度上取决于它”看到”的上下文内容。

传统Prompt Engineering关注的是”单次调用时怎么写指令更好”。而一个真实的Agent任务包含几十上百次调用：不同阶段的子目标提示、工具调用参数生成、失败后的反思与重试、长任务中的阶段性总结。上下文工程（Context Engineering）面对的是整个生命周期的信息管理问题——System Prompt给Agent基础人格与行为准则，工具描述占据Token预算，检索结果涌入上下文，反思记忆需要写入和读出，所有这些都在有限的上下文窗口内竞争空间 $TRAE_REF。

本课将从两个维度展开：

维度 核心问题 对应章节
推理质量 如何让LLM在生成时”想得更深”？ CoT、ToT
输出控制 如何让LLM的输出”格式正确”？ Constrained Decoding
上下文管理 如何在有限窗口内管理爆炸的信息？ System Prompt、Skills、压缩、状态栏
安全边界 如何防止恶意输入劫持Agent？ Prompt注入防御

项目线方面，第03课已确立研究助手的推理循环架构，本课将为其设计完整的上下文工程方案——从System Prompt模板到Skills按需加载，从输出格式控制到安全防护层。

一、CoT推理链构造

⏱️ 理论推导 15min（本节约5min）

1.1 从直接回答到推理链

【必须掌握】 CoT（Chain-of-Thought）的核心思想是：不让LLM直接给出答案，而是让它先写出推理过程，再基于推理过程给出答案。

考虑一个数学问题：”图书馆有3个书架，每个书架有5层，每层放40本书，图书馆共有多少本书？”

  • 直接回答：600（可能出错，尤其对复杂问题）
  • CoT回答：3个书架 × 5层/架 = 15层；15层 × 40本/层 = 600本。答案是600。

CoT的有效性可以从概率角度理解。设问题为 $q$，答案为 $a$，推理过程为 $r$：

$$P(a \mid q) = \sum_r P(a \mid r, q) \cdot P(r \mid q)$$

直接生成时，模型需要一步从 $q$ 跳到 $a$；而CoT将这个”跳跃”分解为先生成 $r$ 再生成 $a$。当推理链 $r$ 正确时，$P(a \mid r, q) \gg P(a \mid q)$，因为条件信息量大幅增加。这种”分步计算”利用了Transformer自回归生成的特性——每生成一个token，它就成为后续生成的上下文，相当于给模型提供了一个”外部记忆”来暂存中间结果。

1.2 Zero-shot CoT触发机制

【应当理解】 Zero-shot CoT的触发极其简单——在Prompt末尾添加一句魔法咒语：

这句提示词的作用机制是激活模型在预训练数据中学到的”分步推理”模式。Wei等人 $TRAE_REF 发现，这种方法在数学推理、逻辑推理等任务上显著提升准确率，且不需要任何示例。

为何有效？ 预训练数据中包含大量”分步解题”的文本（教材、论文、教程）。”step by step”这个短语在训练数据中与分步推理高度共现，起到了模式激活的作用——类似于在模型的概率空间中定位到”推理模式”的区域。

1.3 Few-shot CoT

【必须掌握】 Few-shot CoT通过在Prompt中提供带推理链的示例来引导模型：

Few-shot CoT相比Zero-shot CoT有两个优势：

  1. 格式控制：示例定义了推理链的格式和粒度
  2. 风格迁移：示例的推理风格会被模型模仿

工程要点：示例的推理链质量直接决定效果。劣质示例（如跳步、逻辑错误）会导致模型学到错误的推理模式。

对于Agent场景，CoT通常嵌入在System Prompt中作为行为规范：

这正是第03课ReAct模式的基础——ReAct的Thought部分本质上就是CoT推理链在Agent循环中的应用。第03课关注的是循环的控制结构（状态机、终止条件），本课关注的是如何设计Prompt让推理链的质量更高。

项目线关联：研究助手Agent在分析文献时，需要多步推理（”先搜索→再筛选→再提取关键信息→再综合分析”）。CoT确保每一步推理都有明确的中间状态记录，便于反思机制（Reflexion）在出错时定位问题环节。

二、ToT树搜索推理

⏱️ 理论推导 15min（本节约5min）

2.1 从线性推理到树搜索

【必须掌握】 CoT是线性推理——一条链走到底。但复杂问题可能需要探索多条路径，评估哪条路径最有希望，甚至回溯重试。ToT（Tree-of-Thoughts） $TRAE_REF 将推理过程建模为树搜索问题：

形式化地，ToT维护一棵搜索树，每个节点 $s$ 代表一个”思维状态”（partial solution）。四个关键操作：

操作 定义 公式
思维生成 从当前状态生成 $k$ 个候选下一步 ${s^{(1)}, …, s^{(k)}} \sim p_\theta(s \mid \text{prompt, state})$
状态评估 评估状态的价值/可能性 $V(s) \sim p_\theta(V \mid \text{prompt, state})$ 或 $V(s) \in {1,2,…,L}$
搜索算法 决定探索哪个分支 BFS 或 DFS
终止条件 到达叶节点或价值足够高 $V(s) \geq \theta$ 或 $d = d_{\max}$

2.2 BFS vs DFS策略选择

【必须掌握】 ToT的两种核心搜索策略：

广度优先搜索（BFS）：

BFS适合浅而宽的问题——分支数有限、每层都有多个有价值的候选。例如创意写作（多种开头都值得探索）、24点游戏（多种运算组合）。

深度优先搜索（DFS）：

DFS适合深而窄的问题——需要多步推理、但每步的最优选择比较明确。例如数学证明（每步推导通常只有少数合理选择）、编程问题（算法设计需要层层深入）。

2.3 状态评估函数设计

【应当理解】 状态评估是ToT的关键——它决定了搜索的方向。两种评估方式：

数值评估：让LLM对状态打分（如1-10分或0-1概率）

投票评估：让LLM从多个候选中”投票”选出最优

2.4 CoT vs ToT选型决策

维度 CoT ToT
推理结构 线性链 树搜索
Token消耗 低（单条路径） 高（k×深度 次生成 + 评估）
适用问题 步骤明确、无需回溯 需要探索、可能走错路
实现复杂度 低（一句Prompt） 高（搜索框架 + 评估函数）
典型场景 数学计算、事实问答 创意写作、策略游戏、复杂规划

工程经验：在Agent场景中，CoT是默认选择（成本低、效果稳定）。ToT适用于规划阶段——当Agent需要从多种策略中选择时，用ToT探索几条路径，选定方向后再用CoT执行。这本质上是第03课Plan-and-Execute模式中Planner的增强：用ToT做规划，用CoT做执行。

项目线关联：研究助手Agent在规划文献综述策略时，可以用ToT探索多种检索路径（按关键词检索→按引用网络检索→按时间线检索），评估每种路径的潜在价值，选择最优策略后再用ReAct循环执行。

三、结构化输出控制——Constrained Decoding

⏱️ 理论推导 5min + 工程实践 5min

3.1 为什么需要结构化输出

【必须掌握】 Agent的下游处理（工具调用、状态更新、结果解析）依赖LLM输出的结构化数据。纯Prompt方式（”请以JSON格式回答”）存在严重的可靠性问题：

据统计，纯Prompt方式在生产环境中的解析错误率约为1-5% $TRAE_REF。对于Agent系统——每次任务可能涉及数十次LLM调用——累积错误率会急剧上升。

3.2 JSON Schema约束

【应当理解】 JSON Schema定义了输出的结构契约：

工程要点：注意 reasoning 字段——它给模型留出”思考空间”。如果Schema过于严格（如直接要求 {"answer": int}），模型在第一个token就被迫给出答案，没有推理余地。最佳实践是在Schema顶部包含一个 reasoning 或 thought 字段作为scratchpad $TRAE_REF。

3.3 Constrained Decoding的FSM原理

【必须掌握】 Constrained Decoding是推理时技术——在每一步解码时，强制LLM的输出符合给定约束。其核心机制是logit masking：

$$\text{logit}’(t_i) = \begin{cases} \text{logit}(t_i) & \text{if } t_i \in \text{ValidTokens}(s) \ -\infty & \text{otherwise} \end{cases}$$

$$P(t_i) = \frac{e^{\text{logit}’(t_i)}}{\sum_j e^{\text{logit}’(t_j)}}$$

其中 $s$ 是约束自动机的当前状态，$\text{ValidTokens}(s)$ 是该状态下所有合法的token。

关键特性：模型的相对偏好被保留——如果”hello”和”world”都是合法token，它们的概率比值不变，只有非法token被归零。因此输出质量几乎不受影响，只是被限制在合法空间内。

3.4 约束自动机：从Schema到FSM

【应当理解】 不同约束类型对应不同自动机：

约束类型 自动机模型 构造过程 典型用途
正则表达式 DFA（确定性有限自动机） regex → NFA（Thompson构造）→ DFA（子集构造）→ 最小化DFA 电话号码、日期、ID格式
JSON Schema JSON Schema Walker 递归解析Schema构建状态转移 API响应、工具调用参数
上下文无关文法（GBNF/EBNF） PDA（下推自动机） 文法规则直接编码 SQL查询、DSL、代码片段

以正则表达式约束为例，从regex到DFA的完整流程：

在解码时，DFA维护当前状态。每生成一个token，DFA查询该状态下所有合法的转移字符，将不匹配的token logit设为 $-\infty$。

3.6 推理模型的约束策略

【应当理解】 对于推理模型（如o1/Claude extended thinking），直接对整个输出施加约束会抑制推理能力——模型需要自由生成思维链，不能在第一个token就强制结构化。

两阶段策略：模型先在 <think>...</think> 标签内自由推理（不加约束），然后转入约束状态机生成结构化答案。这正是OpenAI o1系列和Anthropic扩展思考的工作方式 $TRAE_REF。

项目线关联：研究助手Agent使用Constrained Decoding确保工具调用参数格式正确。采用两阶段策略——先让模型推理（Thought），再约束输出工具调用格式（Action）。

【应当理解】 Few-shot示例能显著提升Agent的行为一致性。但示例设计有讲究：

5.3 Skill定义示例

5.4 Skills与工具列表的协同管理

【应当理解】 Skills和工具是两个不同层次的概念，需要协同管理：

协同设计原则：

  1. Skill关联工具：每个Skill声明它需要的工具子集
  2. 工具按Skill加载：未激活Skill的工具不进入上下文
  3. Skill间隔离：不同Skill的工具和指令不交叉污染

【知晓即可】 2026年前沿实践提出了一种更激进的隔离方案——不将Skill内容加载到主上下文，而是fork出独立的子Agent上下文执行 $TRAE_REF：

这种模式确保主上下文永远不被Skill内容污染，代价是子Agent调用增加延迟。

项目线关联：研究助手Agent设计3个Skill——literature-review（文献综述）、citation-analysis（引用网络分析）、trend-report（趋势报告）。默认只加载元数据（~300 Token），用户触发具体任务时才加载完整指令。基础工具（search_papers）始终可用，Skill专属工具（analyze_citation_network）按需加载。

6.2 主动压缩方法

【必须掌握】 上下文压缩的核心是在保留关键信息的前提下减少Token占用。三种主要策略：

策略1：滑动窗口 + 摘要

策略2：选择性保留

消息类型 保留策略 理由
System Prompt 始终完整保留 Agent的行为基础
用户核心指令 完整保留 任务定义
工具调用结果 摘要保留 数据太长，保留结论
Agent推理过程 可删除 中间推理无需保留
错误和重试 删除 失败路径无价值
最终答案 完整保留 任务产出

策略3：结构化状态提取

6.3 信息损失权衡

【必须掌握】 上下文压缩的本质是有损压缩——必须在Token节省和信息保真之间权衡：

工程经验法则：

  • 保留最近5-10轮对话的完整内容
  • 摘要应包含：任务目标、关键决策、已完成步骤、待办事项、重要数据引用
  • 压缩阈值设为上下文窗口的60%（而非100%），为新内容预留空间
  • 对关键工具调用结果单独保留，不纳入摘要压缩

项目线关联：研究助手Agent在执行长时间文献综述任务时，使用滑动窗口+摘要策略。每完成一轮检索后，将检索结果压缩为结构化状态（已检索关键词、找到的论文列表、已筛选结果），保留最近3轮完整对话。

七、Agent状态栏技术

⏱️ 工程实践 20min（本节约2min）

7.1 让Agent感知执行环境

【应当理解】 传统Agent只”看到”对话内容，对执行环境一无所知——不知道当前时间、不知道用户的工作状态、不知道系统资源状况。状态栏技术（Status Bar）将环境信息注入上下文，让Agent做出更智能的决策 $TRAE_REF。

7.2 状态栏的设计模式

状态栏信息分层：

层级 信息类型 示例 更新频率
系统层 时间、会话ID、Token用量 “Token: 45K/128K (35%)” 每轮
任务层 进度、已完成步骤、待办 “步骤3/5：正在分析引用网络” 每轮
环境层 用户时区、工作时段、语言 “用户时区：UTC+8，工作时段” 每会话

参考答案

题1 参考答案

CoT的概率分解：

$$P(a \mid q) = \sum_r P(a \mid r, q) \cdot P(r \mid q)$$

直接生成时模型需要从 $q$ 直接跳到 $a$，中间步骤被”压缩”到模型的隐式计算中。CoT通过先生成 $r$ 再生成 $a$，将计算分解为两步：

  • $P(r \mid q)$：生成推理链，模型擅长此任务（预训练数据包含大量分步推理）
  • $P(a \mid r, q)$：给定推理链生成答案，条件信息量增加，概率大幅提升

原因是Transformer自回归生成中，每生成一个token就成为后续上下文，相当于”外部化”了中间计算结果。

ToT的改进：CoT只采样一条路径 $r$，如果走错了无法回溯。ToT生成 $k$ 条路径 ${r^{(1)},…,r^{(k)}}$，通过评估函数 $V(s)$ 选择最优路径：

$$P_{\text{ToT}}(a \mid q) = P(a \mid r^, q) \cdot P(r^ \mid q), \quad r^* = \arg\max_i V(r^{(i)})$$

当最优路径 $r^*$ 的质量显著高于CoT随机采样的路径时，$P_{\text{ToT}}(a \mid q) > P_{\text{CoT}}(a \mid q)$。

题2 参考答案

  • 用 $-\infty$ 而非0：softmax公式 $P(t_i) = \frac{e^{\text{logit}(t_i)}}{\sum_j e^{\text{logit}(t_j)}}$。如果logit设为0，则 $e^0 = 1$，该token仍有非零概率。设为 $-\infty$ 则 $e^{-\infty} = 0$，概率严格为0。
  • 相对偏好保留：对于两个合法token $t_1, t_2$，$\frac{P(t_1)}{P(t_2)} = \frac{e^{\text{logit}(t_1)}}{e^{\text{logit}(t_2)}}$，与无约束时相同。Mask只影响非法token，合法token间的相对概率不变。
  • 无合法token：说明约束自动机与tokenizer不兼容——例如语法要求输出字符”f”但tokenizer没有单独的”f”token。处理方式：回退到字符级生成（慢但正确），或在编译时预处理语法与tokenizer的兼容性。

常见错误模式：

  • 误认为logit设为0就能禁止token（实际仍有概率）
  • 误认为Constrained Decoding会改变模型的输出偏好（只限制范围，不改变范围内的偏好）

题3 参考答案

层级 名称 Token消耗 加载时机
Level 1 元数据 ~100 Token/技能 始终加载（发现阶段）
Level 2 完整指令 <5K Token/技能 匹配时加载（使用阶段）
Level 3 附属文件 按需 调用时加载（执行阶段）

不能全部放进System Prompt的原因：

  1. Token成本：10个Skill × 5K = 50K Token，占128K窗口的39%，每次调用都付费
  2. 注意力干扰：大量无关内容干扰Attention（第02课的O(n²d)复杂度），”Lost in the Middle”
  3. 指令冲突：不同Skill的指令可能互相矛盾，全部加载导致行为混乱
  4. 维护困难：修改一个Skill需要重新构建整个System Prompt

题4 参考答案

  • 压缩阈值：128K × 60% ≈ 77K Token。预留40%给新内容（检索结果、Agent推理）。不应等到100%才压缩，否则新内容无处放置。
  • 滑动窗口：保留最近8-10轮（约15-20K Token）。覆盖一个完整的子任务周期（检索→分析→总结），确保近期上下文连贯。太少（如3轮）会导致上下文断裂，太多（如20轮）压缩率低。
  • 摘要必含信息：
    • 用户核心需求（任务定义不能丢失）
    • 已完成的检索步骤和关键词（避免重复检索）
    • 找到的关键论文列表（论文ID+标题，用于后续引用）
    • 关键发现和结论（分析结果）
    • 待办事项（未完成的子任务）
    • 遇到的错误和解决方案（避免重蹈覆辙）
  • 跨轮引用问题：第5轮的发现被压缩为摘要中的一句话，第40轮引用时可能缺少细节。缓解方案：
    1. 将关键发现的结构化数据（论文ID、数据值）存入外部状态文件，不纳入压缩
    2. 摘要中对关键发现标注”[详见步骤N]”，Agent可按需重新检索原始数据
    3. 使用结构化状态提取（7.3节策略3）替代自然语言摘要

常见错误模式：

  • 压缩阈值设为100%（导致溢出时无法处理）
  • 摘要只保留”做了什么”而不保留”发现了什么”（信息损失过大）
  • 不保留论文ID等结构化引用（后续无法追溯）
