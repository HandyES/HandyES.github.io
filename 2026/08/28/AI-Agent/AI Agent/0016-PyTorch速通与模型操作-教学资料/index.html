1.2 动态计算图：PyTorch的”记账”方式

PyTorch是**动态图（define-by-run）**框架：你写普通Python代码，每执行一个张量运算，PyTorch就在幕后记一笔账——节点是运算，边是数据依赖。

1.3 链式法则：一行数学，整个自动微分的灵魂

标量情形：若 z = f(y)，y = g(x)，则

$$\frac{\partial z}{\partial x} = \frac{\partial z}{\partial y} \cdot \frac{\partial y}{\partial x}$$

代入上面的例子——先用解析法打样：z = y² = (3x)² = 9x²，直接求导 dz/dx = 18x = 36。再用链式法则：backward()发生时 y = 6，所以

$$\frac{dz}{dx} = \underbrace{2y}{\partial z/\partial y,=,12} \cdot \underbrace{3}{\partial y/\partial x} = 36$$

手算、运行、解析三方一致。链式法则的机械计算就是这么简单。

**那工程上为什么还会算错？**看这个变体（课堂陷阱——先自己手算再往下读）：

一位同学手算：∂z/∂y · ∂y/∂x = x · 2 = 6——运行结果却是 12，少了一半。错在哪？

错在图的结构：z = x·y 中，z对x有两条路径（直接项x，以及间接项y=2x）。链式法则的乘积形式只覆盖”链”（一条路）；分叉节点需要全导数公式——对每条路径分别求积，再求和：

$$\frac{dz}{dx} = \underbrace{x \cdot 2}{\text{经y的路径：}\partial z/\partial y \cdot dy/dx} + \underbrace{y}{\text{直接路径：}\partial z/\partial x} = 6 + 6 = 12$$

解析验证：z = x·(2x) = 2x²，dz/dx = 4x = 12 ✓。

Autograd不需要你区分链与分叉——反向模式把传播到x的所有路径梯度累加（这正是1.4节”梯度累加”语义的节点级预演）。人算错，几乎总是错在”数错了路径”，而不是”乘错了数”。

这个陷阱案例的教学结论：链式法则的机械计算很简单，工程错误总是出在”图记了什么、x到z有几条路径”。这正是”概念理解（非实现）”层级的含义——你要能审计计算图（print(z.grad_fn)、print(y.grad_fn)），而不是能手写autograd（见课后习题B1）。

1.4 向量情形：Jacobian与backward()的真实语义

深度学习里损失L是标量、参数W是矩阵。链式法则升级为：

$$\frac{\partial L}{\partial W} = \frac{\partial L}{\partial \mathbf{z}} \cdot \frac{\partial \mathbf{z}}{\partial W}$$

其中 ∂z/∂W 是Jacobian矩阵。Autograd对backward()的实现是反向模式自动微分：从标量L出发反向传播，每步只需”向量×Jacobian”（而不是构建整个Jacobian）——这就是为什么计算loss.backward()的内存开销与参数量成正比、而非与参数量的平方成正比。

架构师需要带走的三个结论（第17课直接使用）：

  1. 梯度是”账本”的副产品：requires_grad=False的参数不记账、不产生梯度——LoRA冻结W₀（requires_grad=False）只训练B和A，正是利用这一点把可训练参数压缩两个数量级
  2. backward()只能在标量上调用（或对每个元素提供权重）——训练脚本里永远是loss.backward()，loss是标量
  3. 梯度累积在.grad上不清零：连续两次backward()会累加——这就是为什么训练循环里必须有optimizer.zero_grad()。第17课读脚本时看到这行不要奇怪

3.1 Embedding模型调用：三种pooling的工程含义

mean pooling的正确实现必须带attention_mask（padding位置的向量是噪声，不能平均进去）——这是最常见的自实现bug：

归一化与相似度（回收第06课）：cos相似度在归一化后等价于点积：

$$\cos(u, v) = \frac{u \cdot v}{|u| , |v|} = \hat{u} \cdot \hat{v} \quad (\hat{u} = u/|u|)$$

五、推理优化：torch.compile与图模式

5.1 为什么需要编译：Python开销的账

eager模式（逐算子调度执行）每次调用都经过Python调度→算子分发→内核启动。小batch、多层小算子场景，调度开销可达30%+。torch.compile的解法：把整个前向捕获成一张图，做算子融合与内核优化后执行。

算子融合的本质收益是显存带宽：中间结果不落显存。Embedding模型（512维、多层）在批量推理时收益典型在1.3~2倍，生成式LLM交给第19课的vLLM（compile在其中的角色届时展开）。

5.2 torch.compile配置：模式与旋钮（必须掌握）

模式 编译时间 收益 适用
default 中 通用1.3~2× 起步默认
reduce-overhead 中 小batch显著 批量Embedding编码
max-autotune 长（分钟级） 再+10~20% 稳定生产模型

torch.compiler.set_stance()（PyTorch 2.6+引入，Beta）——全局编译姿态旋钮，运行时切换eager与compiled而不必维护两份模型：

架构师用法：上线前用它做A/B测量，上线后用它做逃生门——compiled路径出现数值异常或环境不兼容时，配置开关一键回退eager，无需回滚发版。

5.3 重编译：compile的隐藏成本

compile不是一次性的。PyTorch在编译时记录guard条件（输入shape、dtype等），运行时输入变化触发条件失效→重编译。Embedding服务的典型坑：seq_len随查询长度浮动（10、23、47……）→每次新shape都触发重编译→服务延迟毛刺。

工程解法（第19课会深化）：

动态图vs静态图决策（大纲要求的选择能力）：

场景 选择 理由
模型结构固定、输入形状可桶化 compile 收益稳定，重编译可控
输入形状高度离散、服务冷启动敏感 eager或dynamic=True 避免重编译风暴
一次性的离线批处理 compile（max-autotune） 编译成本被批量摊薄
原型/调试阶段 eager 报错信息可读（compile报错难懂）

九、参考答案

A组（标准答案）

A1：L = 2z = 2(y)² = 2(x+1)²。∂L/∂x = 4(x+1) = 4×4 = 16。链式分解：∂L/∂z=2，∂z/∂y=2y=8，∂y/∂x=1，乘积2×8×1=16。验证：x.grad → tensor([16.])。

A2：两处缺失：

  • model.eval()——若模型含Dropout则前向随机丢弃，同输入不同输出（BGE等纯Encoder模型未必有Dropout，但这是通用纪律，且BatchNorm统计模式同理）
  • torch.no_grad()或torch.inference_mode()——后果较隐蔽：功能上结果可复现，但每次前向记账浪费内存与时间，且pooler_output会携带grad_fn，后续张量操作被autograd追踪（可能触发”Trying to backward through the graph a second time”类错误）
  • 另可指出：model未.to(device)导致CPU推理（性能问题而非正确性问题）

A3：三个雷：

  1. dynamic_axes缺失——batch/seq形状烧死，线上变长输入直接报错（清单第2项）
  2. opset_version=9过低——现代注意力的融合算子（如SDPA相关）不在opset 9算子集，导出失败或静默降级为低效实现（清单第1项）；应≥17
  3. forward中data-dependent控制流（if mask.sum() == 0）——Python分支依赖运行时张量值，图捕获失败（清单第3项）；需改写为torch.where静态等价
    隐含第四雷：清单第5项——tokenizer与pooling不在图内，部署侧需复现，评审应要求附一致性验证脚本（assert_allclose）。

B组（参考方案）

B1：
①错在把z对x的依赖当成单链——z = x·y中x通过两条路径影响z（直接项x + 经y的间接项），单链链式乘积 ∂z/∂y·∂y/∂x = x·2 = 6 只算了间接路径，漏掉直接项。
②方法一（全导数）：dz/dx = ∂z/∂y·dy/dx + ∂z/∂x = x·2 + y = 6 + 6 = 12；方法二（解析）：z = x·(2x) = 2x²，dz/dx = 4x = 12 ✓——解析法永远可以充当第三方仲裁。
③调试流程：print(z.grad_fn) → MulBackward0（z是乘积节点）；print(y.grad_fn) → MulBackward0且y.requires_grad=True（y依赖x）；手绘DAG：x→y→z与x→z共两条边；torch.autograd.grad(z, x)交叉验证得12。
④预测：z = y·y = (2x)² = 4x²，dz/dx = 8x = 24（x=3）。路径视角：z的两个因子都是y，各贡献 ∂z/∂yᵢ·dy/dx = y·2 = 12，两条路径合计24——因子复用使路径数照常翻倍。运行验证：tensor([24.]) ✓。
⑤通用原则：手算与运行不符时，先审计”图记了什么、有几条路径”（打印grad_fn链/手绘DAG/数边），再怀疑数学；链式法则只覆盖链式结构，分叉与因子复用节点必须”逐路径求积、跨路径求和”——反向模式的梯度累加语义正是为此设计。

B2：根因：查询长度离散变化（seq_len 10/23/47…）触发guard失效→重编译风暴（每次重编译秒级~分钟级，阻塞推理）。候选修复：

  1. torch.compile(model, dynamic=True)——一次编译适配动态shape；代价：优化保守，加速比降约10~30%
  2. 输入padding到固定桶（{32,64,128}）+桶内静态shape；代价：浪费少量计算（pad开销），实现需改数据入口
  3. 查询期直接放弃compile走eager（set_stance("force_eager")运行时切换，5.2节）；代价：失去加速，但P99稳定——延迟稳定性>平均加速的在线服务原则
    组合拳：桶化+dynamic兜底；入库期批处理保留max-autotune。

B3：根因：v4的apply_chat_template为兼容旧代码返回裸input_ids（list/tensor）；v5统一返回BatchEncoding（含input_ids+attention_mask等）。旧代码model(ids)在v5下传入的是dict→forward()收到意外类型参数→TypeError（或attention_mask缺失告警）。修复patch：

合理性论证：①裸ids丢弃了attention_mask——多轮模板padding场景下模型会把pad token当真实token注意力（正确性bug）；②v4时代用户普遍踩这个坑后仍需手动重新encode；③统一BatchEncoding使apply_chat_template与tok(...)行为一致（”同一枚硬币的两面”——v5设计哲学：encode/decode对称、模板/编码对称）——短痛换长一致。

关键决策与理由：

  1. Protocol而非继承——上层零依赖（第05课工具Schema同思路：契约驱动）
  2. 级联灰区条件复用CRAG阈值——评估降级链一致，避免两套阈值漂移
  3. 降级链路：本地加载失败→RemoteEmbedder兜底（需隐私审批过的私有化API）→最终返回”检索不可用”明确错误（宁可明确失败，不可静默降质——第14课MAST”工具输出未验证”教训）
  4. 版本治理：阈值与模型版本同库存储（配置项{model_version: {theta_hi, theta_lo}}），灰度放量前跑离线评估集重校（第10课统计显著性纪律）
  5. 缓存失效：文档内容hash而非ID入键——文档未变ID变（重建索引）仍命中；文档变则自然miss；90天全量重编码=清空版本命名空间（7.3场景约束）

常见错误模式（评分参考）：

  • 阈值与模型版本不绑定→换模型后沿用旧阈值，级联路由系统性错误
  • 缓存键不含版本→新模型读到旧模型向量，相似度语义错乱（静默数据污染）
  • 降级链终点返回空列表而非显式错误→上层误判”无相关文档”，CRAG走incorrect分支浪费LLM调用
  • 本地/远程返回维度不同却共用缓存层→维度不匹配在检索期才爆炸
  • 级联升级无采样与指标→成本黑洞（不知道多少流量升级到LLM）
