一、为什么需要MCP：从”进程内函数”到”协议服务”

时间预算：4分钟

1.1 M×N集成问题：没有协议时的世界

第05课我们学过Function Calling：每个LLM厂商定义自己的工具调用格式，Agent开发者把工具函数注册给LLM。这套机制在单Agent+自研工具场景下运转良好。但把镜头拉远，看一个企业里真实发生的问题：

MCP（Model Context Protocol）的核心承诺：把M×N降为M+N。工具方只实现一次MCP Server，客户端方只实现一次MCP Client，中间的协议层由标准定义。这就是”AI领域的USB-C”比喻的准确含义——不是”万能接口”，而是标准化了连接形态，让生态两侧可以独立演进。

1.2 协议分层：MCP站在谁的肩膀上

注意最底层的选择：MCP没有发明新的消息格式，直接用JSON-RPC 2.0——这是一个1990年代XML-RPC思想在JSON时代的延续、经过二十年生产验证的轻量RPC标准。协议设计的第一个工程判断：能复用成熟标准的绝不发明新标准。 这与第01课Harness工程”编排”功能的设计哲学一脉相承。

1.3 一个容易混淆的问题：MCP vs Function Calling

学完第05课的同学最常问：“Function Calling不已经是工具调用标准了吗，MCP解决什么？”

维度 Function Calling（第05课） MCP（本课）
定位 LLM API层的输出格式约定 进程间的通信协议
作用范围 单个LLM请求内（模型决定调哪个函数） 跨进程、跨机器、跨组织
工具在哪里 与Agent同进程（你写的Python函数） 独立进程/独立服务器
谁消费工具描述 LLM MCP Client（通常是Agent宿主）
关系 互补：MCP Server的工具经tools/list暴露给Client，Client再以Function Calling形式注册给LLM

所以准确的说法是：Function Calling标准化了”模型↔工具描述”的语义，MCP标准化了”Agent↔工具服务”的连接。两者在架构图中前后相接，不是竞争关系。

二、MCP v2.0无状态核心（2026-07-28规范）

时间预算：7分钟

2.1 v1协议的三大工程痛点

MCP v1（2024-11发布，2025-06与2025-11两次修订）是一个有状态双向协议。所谓”有状态”，指协议本身维护跨请求的连接状态；所谓”双向”，指不仅client可以请求server，server也可以反过来请求client。这两个设计在原型阶段很优雅，在生产环境却变成三个具体的痛点：

痛点1：连接握手。v1要求每次连接先执行initialize/initialized交换——协商协议版本、交换能力清单。一个短生命周期的client（比如跑完一次就退出的CLI脚本）也要付出完整握手成本。

痛点2：会话粘性。v1的Streamable HTTP传输用Mcp-Session-Id头标识会话。负载均衡器必须保证同一会话的请求落到同一实例（session affinity/粘性路由）：

痛点3：双向流。v1允许server主动向client发起请求——sampling（让client的LLM帮server补全文本）、elicitation（向用户提问）、roots（询问文件系统根）。这些请求要求持续保持打开的双向流，与”请求-响应”的普通HTTP负载模型冲突。

2.2 无状态核心：v2.0的答案（必须掌握）

2026-07-28规范的headline变更：MCP从有状态双向协议转变为无状态请求/响应协议。三个具体机制：

机制1：请求自描述。每个请求在_meta字段中携带自己的协议版本、客户端身份、客户端能力——服务端不依赖任何先前请求留下的记忆就能处理它：

机制2：握手退役。initialize/initialized交换与Mcp-Session-Id头正式删除（SEP-2575/SEP-2567）。能力信息不再在握手时协商，而是随每个请求在_meta中自报。

机制3：能力发现改为可选RPC。想提前知道server能力的client可以调用新增的server/discover方法（一次调用返回支持的版本、能力、身份），但这不是必须的——client完全可以直接发起tools/call，遇到版本不匹配错误再处理。

三个机制合起来的效果，官方表述是：”任何请求可以落在负载均衡器后面的任何实例上，无需共享存储“。v1的痛点2（会话粘性）从协议层面被消除——这是”无状态”三个字的真实工程含义：

2.3 状态管理迁移方案：显式handle模式（必须掌握）

一个关键的辨析：“协议无状态”≠”应用无状态”。官方规范的原话翻译过来是：”删除协议级session并不强制你的应用变成无状态的。如果你的server需要跨调用携带状态，从工具中铸造一个显式handle，让模型把它作为参数传回来。”

这句话是v2.0迁移工程的灵魂，展开讲：

官方设计者给出的理由值得背诵：“模型可以看见handle并在工具之间传递它”——这比藏在transport里的session状态更好。本质上，这是把状态管理从协议层上移到业务层，让状态成为Agent推理循环的一等公民（第03课：状态应显式化，隐式状态是调试地狱）。

handle的工程设计要点（结合第09课记忆系统）：

设计点 推荐做法 反例
命名 带类型前缀的可读ID：srch_9f3a、sess_a82b 自增整数42（无类型语义）
生命周期 TTL+LRU淘汰（复用第09课遗忘曲线思想） 永不过期（内存泄漏）
存储 共享存储（多实例可消费）或编码自描述数据 单实例内存dict（粘性回来了）
传递方式 作为工具参数显式传递 塞进自定义HTTP头（又藏起来了）

2.4 双版本共存：迁移不是断崖

规范的breaking change很多，但生态没有断崖——同一个Server同时服务两代客户端：2026时代的client发无状态请求，2025时代的client仍走initialize握手，同一进程两种都能答。SDK v2的Client自动处理这个探测：先试server/discover，失败则回退老握手。

工程启示：协议演进的关键不是”新版本多先进”，而是”旧版本能活多久”。配套的正式弃用政策规定了最少12个月的弃用窗口——Roots、Sampling、Logging等被弃用的特性至少还能工作一年。做架构师评审迁移方案时，第一问永远是：”存量客户端的退场时间表是什么？”

三、三大原语：设计哲学与接口契约

时间预算：8分钟

协议无状态化解决的是”怎么传消息”；三大原语回答的是”传什么消息”。MCP把服务端能力抽象为三个原语（primitive），区分它们的标准不是数据类型，而是控制权归属：

为什么一个协议需要三个原语而不是一个”万能工具”？ 因为Agent系统里有三类决策主体（模型/应用/用户），它们的权限边界必须显式区分：模型不该有权决定挂载哪个数据源（那是应用的安全边界），应用不该替用户决定用哪个提示模板（那是用户的表达自由）。第04课”上下文工程”的三级注入（系统级/应用级/用户级）在协议层的投影，就是这三大原语。记住这个对应关系，原语设计哲学就不再是死记硬背。

3.1 Tools：模型控制的原语

Tools与第05课的Function Calling直接对接——tools/list返回的工具目录，MCP Client转换为LLM的function定义；LLM决策调用时，Client发起tools/call。

JSON-RPC接口契约：

契约细节中最值得架构师注意的一条：工具执行失败 ≠ 协议错误。isError: true的结果仍包含content，模型能读到”检索超时，建议缩小关键词范围”这样的错误描述，进而调整策略重试——这正是第05课”错误处理FSM”在协议层的落点。而JSON-RPC层面的error响应（如INVALID_PARAMS）则意味着请求本身不合法，Client应视为bug处理而非让模型重试。两层错误语义的分离，是所有RPC协议设计的通用智慧。

3.2 Resources：应用控制的原语

Resources把”数据源”标准化：文件内容、数据库行、API响应，统一抽象为URI标识的只读资源。

URI模板必须是严格的RFC 6570（v2.0 SDK行为：{+path}、{?query}等标准展开符，模板非法在注册时即报错，路径穿越值默认拒绝——这是从v1”宽松正则匹配”收紧的安全修复，呼应第04课输入消毒）。

Tools vs Resources的选型判断（架构师高频决策）：动作（有副作用、需参数、模型主动调用）用Tool；上下文（只读、被注入、应用主动挂载）用Resource。文献检索是动作（search_papers工具）；最近入库列表是上下文（papers://recent资源）。

3.3 Prompts：用户控制的原语

Prompts把”可复用的提示模板”做成协议原语——带参数的用户可发现模板：

ChatGPT的GPTs、Claude的Projects，本质都是这个原语的产品化。研究助手中，”文献综述生成””审稿意见撰写”这类用户主动发起的高频任务适合做成Prompt原语。

3.4 列表缓存：ttlMs与cacheScope（v2.0新机制）

tools/list、resources/list、prompts/list、resources/read的响应现在携带缓存提示（SEP-2549）：

  • ttlMs：建议缓存存活毫秒数（300000 = 5分钟）
  • cacheScope：缓存作用域提示

为什么重要？工具目录可能很大（一个DB网关server暴露数百工具），每次会话重新tools/list是显著开销；缓存后不仅省流量，还稳定了上游LLM的prompt cache（工具描述是system prompt的一部分，目录顺序抖动会使KV Cache前缀全部失效——呼应第02课Prefix Caching与第19课推理优化的经济账）。v2.0同时规定列表结果为确定性顺序，正是为了让prompt前缀逐字节稳定。

四、MRTR、Header路由与Extensions框架

时间预算：5分钟（应当理解）

4.1 无状态的遗留难题：server怎么”问client要东西”

2.1节的痛点3（双向流）在无状态模型下变得更尖锐：sampling/elicitation本质是server向client的请求——“请让你的LLM帮我补全这段”（sampling）、”请向用户确认这个操作”（elicitation）。无状态请求/响应协议里，server没法”反过来发起请求”，怎么办？

**MRTR（Multi Round-Trip Requests，多轮往返请求，SEP-2322）**的答案：把”server问client”改写为”server在响应里提出问题，client带着答案重试”：

架构师视角的洞察：MRTR把交互成本从”保持长连接”转移为”多一次往返”。对交互式Agent（本来就有人类在环）几乎零成本；对无人值守的批处理Agent，elicitation类工具应在工具描述里声明”需要用户交互”让编排层（第12课LangGraph的HITL中断）预先规划。这也是第14课”Proposer-Reviewer前置防御”与第03课”Reflexion后置纠正”对比的又一个实例——人类确认的时机设计贯穿整个Agent工程。

4.3 授权强化（知晓即可）

v2.0在OAuth 2.0授权上做了三项硬化（做企业级部署时知道”该查什么”即可）：

  1. RFC 9207 iss验证（SEP-2468）：授权服务器响应必须带iss（issuer标识），client在兑换code前必须验证——堵住”授权服务器混淆”漏洞（攻击者用A服务器的code去B服务器兑换）。
  2. 凭证绑定issuer（SEP-2352）：client credentials禁止跨授权服务器复用。
  3. DCR弃用→CIMD：动态客户端注册（Dynamic Client Registration）正式弃用，转向客户端元数据文档（Client ID Metadata Documents）——静态、可审计的客户端身份发布方式，更符合企业合规。

4.4 Extensions框架：Tasks、MCP Apps与EMA（知晓即可）

v2.0正式引入扩展（Extensions）框架——核心协议保持精简，增量能力以命名空间扩展形式发布（io.modelcontextprotocol/xxx）。首批官方扩展：

扩展 能力 架构师需要知道的
Tasks 长任务：poll-based tasks/get+tasks/update，变更通知合并为subscriptions/listen单流（SEP-2663） 文献批量下载这类分钟级任务走Tasks扩展，而不是让工具调用挂着等
MCP Apps server向client渲染交互界面 前沿方向：工具不仅返回文本，还能返回UI组件
EMA 企业托管授权 企业IT统一管理MCP授权，不依赖终端用户各自配token

弃用清单（12个月窗口）：Roots（文件系统根）、Sampling（server借用client的LLM）、协议级Logging被弃用（SEP-2577）；ping方法移除；legacy HTTP+SSE传输弃用。新项目不应再采用这些特性——评审存量代码时，见到它们要列入迁移清单。

五、服务发现、网关路由与CAP分析

时间预算：3分钟

5.1 server/discover不是”服务注册中心”

先校准一个容易望文生义的误区：v2.0的server/discover是能力发现RPC，不是微服务意义上的”分布式服务注册中心”（没有etcd/Consul那样的注册表、心跳、健康检查）。它回答的问题是”这个server支持什么”，而不是”哪里有这类server”：

跨server的实例寻址由谁做？ 由网关+DNS+负载均衡的既有Web基础设施做。这正是无状态化的深层意图：MCP不再自建分布式基础设施，而是把自己降格为”普通HTTP工作负载”，把寻址、路由、扩缩容全部外包给Web世界二十年积累的标准件。第01课”Harness工程=复用而非重造”的哲学，在协议尺度上重演。

5.2 网关架构：不持会话的路由器

5.3 CAP分析：无状态化消除了什么、没消除什么

CAP定理回顾（第06课提过其 cousin——一致性模型）：分布式系统在网络分区（P）下，一致性（C）与可用性（A）不可兼得。逐层分析MCP v2.0：

协议层：会话一致性需求被整体消除。v1的session-42要求”下一个请求看到上一个请求留下的状态”——这是强一致需求，实例间需要状态复制或粘性路由，分区时要么牺牲A（拒绝服务）要么牺牲C（状态丢失）。v2.0协议层零状态 → 没有需要一致的协议状态，CAP对协议层不再构成约束。这是”无状态化规避CAP”的准确含义——不是打败了CAP，而是让CAP的问题域空集化。

业务层：CAP问题原封不动地留给了你。显式handle模式把状态推给了业务存储（2.3节）：handle指向的数据放在Redis里，Redis主从分区时，”实例A铸造的handle，实例B读不到”——这就是业务层CAP。标准解法也是标准的：

方案 取舍
单实例内存dict C最强（单点线性一致），A最差（实例挂=状态全丢），仅适合开发环境
Redis主从+哨兵 AP倾向（异步复制，分区时新主可能丢最近写入）
handle自包含编码（把检索结果编码进handle本身，如JWT） 完全无状态（任何实例可解码），代价是handle变大、无法撤销

架构师决策框架：文献检索结果（几KB、可重建、丢了重搜一次）→ 自包含或短TTL共享缓存；用户支付凭证（不可丢、需撤销）→ 强一致存储。状态的CAP属性，应该按业务后果逐项决策，而不是一刀切。

  2. handle过期实验：HANDLE_TTL_SECONDS = 0——第③步立刻报”handle无效”。思考：TTL设多短的代价是什么？多长呢？（联系第09课记忆的τ参数：太短→反复重检浪费Token；太长→状态膨胀+陈旧数据风险。）
  3. 拆掉MRTR安全闸：删掉tool_download_paper中"q1" not in responses分支，直接下载——观察第④步一轮完成。思考：什么让”付费操作无确认”从bug变成事故？（第05课危险操作分级：花钱类=必须确认；对照Q5架构决策练习。）
  4. 观察缓存提示的语义：把tools/list响应的ttlMs从300000改成0——client每次都该重新拉取。思考：工具目录变化频率与prompt cache稳定性的权衡（工具描述进system prompt → 目录抖动 → KV前缀失效，呼应第02课与3.4节）。

7.3 本课小结与项目进度

三个必须带走的设计判断：①无状态化的本质是把状态从协议层上移到业务层（显式handle），而不是消灭状态；②三大原语按控制权（模型/应用/用户）划分，不是按数据类型；③MRTR用”多一次往返”换”无长连接”——交互成本转移而非消失。

九、参考答案

Q1 参考答案

三机制：①请求自描述（_meta携带协议版本/客户端身份/能力）——消除对握手协商（initialize/initialized）的依赖，痛点1连接握手成本；②Mcp-Session-Id与握手正式退役——消除会话粘性约束，痛点2（LB不再需要session affinity，任意实例可应答任意请求，Serverless/Edge可部署）；③server→client请求改MRTR多轮往返——消除持续双向流依赖，痛点3。CAP辨析：v1的session要求跨请求状态一致（强一致需求），分区时必须在C/A之间抉择；v2协议层零状态→没有需要保持一致的协议状态，CAP的问题域在协议层为空集——这是”消除协议层CAP约束”的含义。但业务状态（handle指向的数据、Redis中的存储）依然存在且仍有CAP属性（分区时新写handle可能不可读），所以说”MCP消除了CAP问题”是错的——它只是把CAP问题从协议层赶到了业务层，由架构师按业务后果逐项决策（5.3节表格）。

Q2 参考答案

Tools——模型控制——tools/list/tools/call——例：search_papers（LLM在推理循环中自主决定检索）。Resources——应用控制——resources/list/resources/read——例：papers://recent最近入库列表（宿主应用决定注入会话的上下文）。Prompts——用户控制——prompts/list/prompts/get——例：review-paper审稿模板（用户在UI主动选用）。语义区别：isError:true是正常协议响应，content里携带错误描述，会回填到对话中被模型读到，模型可以据此调整策略（换关键词、缩小范围、换工具）——第05课错误处理FSM的”可恢复分支”；JSON-RPC error（如INVALID_PARAMS）表示请求本身不合法，通常意味着Client实现有bug或版本不兼容，重试同样的请求无意义。对自我纠正的意义：如果工具失败走协议错误，模型永远看不到失败原因，FSM的”重试/降级”转移缺少输入信号，Agent会在同一处反复失败。v2.0 SDK甚至把这一语义做进了类型系统：工具内raise MCPError是协议错误（模型不可见），普通返回值才能被模型消费。

Q3 参考答案（参考方案）

迁移四步：①handle设计——search_papers每次返回srch_<ts>handle指向”最近3次检索”聚合结构；工具描述中显式写明”后续read_paper/refine_query需携带此handle”，让模型学会传递（模型可见性是handle模式的前提）。②存储选型：单实例内存——读写最快但实例故障全丢且多实例不可见，仅开发环境；Redis共享+TTL——多实例可消费、可设10-30分钟TTL，异步复制下分区时最近写入可能丢失（AP倾向），但”检索上下文丢了重搜一次”代价可接受，推荐；自包含编码（JWT式把结果编码进handle）——完全无状态、任何实例可解析，但检索结果几KB使token膨胀、无法撤销、无法更新，仅适合小结果集。③TTL：30分钟（研究对话的典型时长），LRU上限防膨胀——第09课τ参数权衡复用。④模型配合：工具描述加入handle语义；编排层（第12课）在HITL中断恢复时需把handle回填进对话状态。常见错误：把handle塞进自定义HTTP头（又藏回transport层，模型不可见）；handle永不过期（状态膨胀）；迁移时保留旧session代码”兼容一下”（双状态源，一致性噩梦——应利用SDK双版本共存机制，新旧协议各走各的显式实现）。

Q4 参考答案

分工：MCP组合解决单server的水平扩展与连接标准化（discover=能力发现，header=免解析路由，无状态=任意实例应答）；注册中心解决实例寻址与健康状态分发（哪个IP活着、负载多少）。不自建注册中心的原因：①目标场景是”工具服务”而非”通用微服务”——server数量以十计而非万计，DNS+LB+网关足够；②复用Web既有基础设施的成本远低于自建并维护一套注册协议（一致性、心跳、脑裂……全是分布式经典难题）；③生态两侧（SDK、云平台）接入门槛更低。反向瓶颈：当server实例数大到需要动态上下线感知（弹性伸缩分钟级）、跨地域寻址、或需要在多网关间同步路由表时，DNS轮询+静态LB的收敛速度成为瓶颈——此时在网关与实例之间引入注册中心（或直接用K8s Service等平台能力，第20课）。判据：实例变更频率×路由收敛延迟要求，而非绝对实例数。

Q5 参考答案（参考方案）

分层：①边缘层——读Mcp-Method/Mcp-Name头，做路由+粗粒度限流（不解析body）；②策略层——agent_id×server×tool三级权限矩阵（来自权限中心，本地缓存+版本号失效），付费类工具（download_paper）注入”需审批”标记；③执行层——转发至后端server，同步落审计流。授权流程：client带token → 边缘验签+iss校验（RFC 9207）→ 策略层查矩阵 → 付费操作转入审批队列（MRTR input_required+审批系统回调）→ 放行。审计数据模型：ts, agent_id, tenant_id, server_id, tool_name, request_id, latency_ms, status(is_error/result_type), token_cost, args_digest(参数摘要哈希，脱敏)——注意存摘要不存原文（合规），request_id贯穿网关-server-审计三方用于追链。降级：网关双活（无状态所以双活简单）；网关全挂时——只读工具走”直连模式”逃生舱（client配置里预置server直连地址，牺牲治理换可用性），付费/写操作直接拒绝（宁停不乱）。CAP三处：①权限矩阵缓存——最终一致（30s失效窗口内可能用到旧权限，可接受：权限收回延迟）→AP；②审计流——Kafka，至少一次投递，分区时宁可堆积不可丢→CP倾向；③审批状态——强一致（不能两个网关对同一审批得出相反结论）→CP。常见错误：权限判断做在server侧而非网关（每个团队各自实现=治理灾难）；审计存参数原文（合规事故）；没有request_id贯穿（故障排查时对不齐链路）；逃生舱把付费操作也放行（资金损失）。

Q6 参考答案（参考方案）

代码骨架：在handle_request增加resources/list分支（返回URI、name、mimeType清单）与resources/read分支（RFC 6570模板展开papers://{paper_id}/fulltext → 查PAPERS → 返回text/markdown内容）。越权防护：解析出paper_id后，取_meta.clientInfo中的租户字段（如tenant: "team-a"），查PAPER_ACL[paper_id]，不在授权集则返回JSON-RPC error（code -32603或自定义-32001，message”resource not accessible”）而非正常资源内容，且不暴露该资源是否存在（防止枚举探测——响应与”资源不存在”同构）。必须在协议处理层做的理由：①Resources没有”工具实现”——它的读取路径是统一的resources/read，若在各资源处理器里各自判断，新增资源时必然遗漏（安全检查必须在唯一收口处）；②应用控制的资源挂载是宿主的信任边界，越权读取属于协议级违规（请求本身不合法），语义上就是协议错误而非业务错误；③与Tools不同——工具的参数校验失败可以走isError让模型重试，而越权是不该重试的安全事件，应进入审计告警而非对话。评分要点：模板展开正确、ACL检查位置、错误语义选择、防枚举设计、审计联动。
