第03课：Agent推理架构——ReAct、Plan-and-Execute、Reflexion

课程信息

  • 课程名称：AI Agent系统架构设计
  • 本课序号：03/22
  • 预计学习时间：约55分钟（理论推导20min + 工程实现15min + 评估方法5min + 习题15min）
  • 项目贡献：基础架构层——为”企业级智能研究助手Agent系统”设计推理循环架构，确立PDA循环的状态机模型与终止条件
  • 先修要求：第01课（PDA循环定义）、第02课（Attention复杂度、KV Cache、上下文窗口约束）

本课导读

第02课我们分析了LLM的”单次推理”机制——Attention的 $O(n^2d)$ 复杂度、KV Cache的显存占用、上下文窗口的Token预算。但Agent不是”问一次答一次”的聊天机器人，它的核心能力是循环推理：感知任务→推理决策→执行行动→观察结果→继续推理，直到任务完成。

这个循环就是第01课定义的PDA（Perceive-Decide-Act）循环。本课要解决的核心问题是：如何设计这个循环的控制结构，使Agent在有限Token预算内高效、可靠地完成任务？

三种经典推理模式给出了三种回答：

模式 核心思想 类比
ReAct 边想边做，每步重新决策 经验丰富的工匠
Plan-and-Execute 先规划再执行 项目经理
Reflexion 做完反思，下次改进 迭代学习者

本课将从状态机形式化角度统一描述这三种模式，推导各自的终止条件和Token消耗，并融入2026年前沿动态（原生System 2推理、多Agent反思扩展）。项目线方面，将为研究助手Agent设计推理循环架构。

一、ReAct模式——推理与行动的交替循环

⏱️ 理论推导 20min（本节约7min）

1.1 ReAct的核心思想

【必须掌握】 ReAct（Reasoning + Acting）由Yao等人于2022年提出 $TRAE_REF，其核心思想是将LLM的推理（Thought）和行动（Action）交替执行，形成闭环。

ReAct的每次循环由三元组构成：

$$\text{ReAct Step} = \langle \text{Thought}_t, \text{Action}_t, \text{Observation}_t \rangle$$

  • Thought（思考）：LLM以自然语言进行推理，决定下一步做什么
  • Action（行动）：LLM输出结构化的工具调用指令
  • Observation（观察）：工具执行后返回的结果，被注入回上下文

一个完整的ReAct轨迹示例（研究助手场景）：

ReAct的关键特征：每一步都重新推理，不预先承诺多步计划。这使得ReAct对环境变化具有天然的适应性——如果某个工具返回意外结果，Agent在下一步Thought中立即调整策略。

1.2 ReAct的状态机形式化

【必须掌握】 这是本课核心知识点之一——用状态机统一描述推理循环。

ReAct可以形式化为一个确定性有限状态机（DFS）：

$$M_{\text{ReAct}} = (Q, \Sigma, \delta, q_0, F)$$

符号 含义 ReAct定义
$Q$ 状态集合 ${q_{\text{think}}, q_{\text{act}}, q_{\text{observe}}, q_{\text{finish}}, q_{\text{error}}}$
$\Sigma$ 输入字母表 ${\text{task}, \text{tool_result}, \text{timeout}, \text{max_step}}$
$\delta$ 状态转移函数 见下方转移表
$q_0$ 初始状态 $q_{\text{think}}$
$F$ 终止状态集合 ${q_{\text{finish}}, q_{\text{error}}}$

状态转移函数 $\delta$：

当前状态 输入 下一状态 输出
$q_{\text{think}}$ task / observation $q_{\text{act}}$ Thought文本 + Action指令
$q_{\text{act}}$ action $q_{\text{observe}}$ 执行工具调用
$q_{\text{observe}}$ tool_result $q_{\text{think}}$ Observation注入上下文
$q_{\text{observe}}$ timeout / error $q_{\text{error}}$ 错误信息
$q_{\text{think}}$ finish_signal $q_{\text{finish}}$ 最终答案
任意状态 max_step $q_{\text{error}}$ 强制终止

架构决策含义：状态机形式化的价值在于——它使推理循环变成了可验证、可测试的工程组件。你可以为每个状态编写单元测试，为每条转移路径编写集成测试。这是从”Prompt工程”升级到”Agent工程”的关键一步。

1.3 ReAct的Prompt模板设计

【应当理解】 ReAct的Prompt需要严格的结构化设计，确保LLM按Thought-Action-Observation格式输出。

Prompt设计要点：

设计决策 原因 影响
明确的格式标记（Thought/Action/Observation） LLM需要结构提示才能稳定输出三元组 减少解析失败率
工具列表内嵌在System Prompt中 LLM需要知道可用行动空间 增加系统提示Token，但不可省略
Observation由系统注入而非LLM生成 防止LLM编造工具返回结果 确保事实可靠性
finish作为显式工具 给LLM一个明确的”退出信号” 避免Agent无限循环

1.4 ReAct循环的Token消耗分析

【必须掌握】 本节将第02课的公式应用于ReAct循环的成本分析。

回顾第02课的PDA最大步数公式：

$$N_{max} = \frac{W - T_{system} - T_{user} - T_{response}}{T_{step}}$$

ReAct中每步的Token消耗：

$$T_{step} = \underbrace{T_{thought}}{\text{推理输出}} + \underbrace{T{action}}{\text{工具调用}} + \underbrace{T{observation}}_{\text{工具返回}}$$

实例分析（研究助手Agent，128K窗口）：

组件 Token数 说明
$T_{system}$ 2,000 系统提示 + 工具描述
$T_{user}$ 500 研究任务描述
$T_{response}$ 4,000 最终回答预留
$T_{thought}$ 150 每步推理平均输出
$T_{action}$ 50 工具调用JSON
$T_{observation}$ 2,000 工具返回平均（搜索结果/网页内容）
$T_{step}$ 2,200 每步总计

$$N_{max} = \frac{131072 - 2000 - 500 - 4000}{2200} = \frac{124572}{2200} \approx 56 \text{ 步}$$

但这是理论上限。实际中需要预留安全余量（工具返回波动）：

$$N_{safe} = \frac{W - T_{system} - T_{user} - T_{response} - T_{margin}}{T_{step} \times \sigma}$$

其中 $\sigma$ 是安全系数（通常1.2-1.5），$T_{margin}$ 是预留余量。

不同窗口下的ReAct步数对比：

窗口大小 固定开销 每步消耗 理论最大步数 安全步数($\sigma$=1.3)
8K 5,500 2,200 1步 1步
32K 6,500 2,200 11步 8步
128K 6,500 2,200 56步 43步

架构决策含义：8K窗口的模型几乎无法执行ReAct循环——一步就耗尽预算。研究助手Agent需要128K窗口才能支持复杂的多步研究任务。这也是为什么第02课强调上下文窗口是Agent架构的硬约束。

1.5 ReAct循环的终止条件设计

【必须掌握】 这是本课核心知识点之二。ReAct最大的工程风险是无限循环——Agent在相同状态间反复跳转，消耗Token而不产生进展。

终止条件分为三层：

第一层：正常终止

$$\text{Terminate when } \exists t, \text{Action}_t = \text{finish}(\cdot)$$

LLM主动判断任务完成，调用finish工具。这是最理想的终止方式，但依赖LLM的判断能力。

第二层：强制终止（max_steps）

$$\text{Terminate when } t \geq N_{max}$$

设置最大步数上限，作为安全网。$N_{max}$ 的取值基于上节的Token预算分析。

第三层：非进展检测（no-progress detector）

检测Agent是否陷入循环：

$$\text{Terminate when } \exists i < j < k, \text{Thought}_i \approx \text{Thought}_j \approx \text{Thought}_k$$

具体实现使用文本相似度：

$$\text{sim}(\text{Thought}_i, \text{Thought}_j) = \cos(\mathbf{e}_i, \mathbf{e}_j) > \theta$$

其中 $\mathbf{e}_i$ 是Thought的Embedding向量，$\theta$ 是相似度阈值（通常0.85-0.95）。

三层终止条件的工程实现：

架构决策含义：三层终止条件是纵深防御策略——第一层依赖LLM判断（可能失效），第二层是硬性上限（一定生效但可能过早终止），第三层检测循环（精准但计算开销大）。生产系统中三层缺一不可。

二、Plan-and-Execute——任务分解与分步执行

⏱️ 理论推导 20min（本节约5min）

2.1 Plan-and-Execute的核心思想

【必须掌握】 Plan-and-Execute将推理循环拆分为两个阶段：Planner先生成完整计划，Executor按计划逐步执行。

与ReAct的核心区别在于决策时机：

维度 ReAct Plan-and-Execute
决策时机 每步重新决策 计划阶段一次性决策
上下文依赖 依赖完整历史 计划阶段依赖任务，执行阶段依赖计划
Token效率 每步消耗Thought Token 执行步无需Thought，节省Token
适应性 强（随时调整） 弱（需触发重规划）
适用场景 短horizon、探索性任务 长horizon、结构化任务

2.2 任务分解DAG构建

【应当理解】 Plan-and-Execute的计划通常表示为有向无环图（DAG），描述步骤间的依赖关系。

定义：计划 $P = (V, E)$，其中：

  • $V = {v_1, v_2, …, v_n}$ 是步骤集合，每个 $v_i$ 包含操作描述和预期输入/输出
  • $E \subseteq V \times V$ 是依赖边，$(v_i, v_j) \in E$ 表示 $v_j$ 依赖 $v_i$ 的输出

并行执行优势：v1/v2/v3无依赖关系，可并行执行；v4/v5/v6也可并行。这使得Plan-and-Execute在可并行任务上比ReAct（严格串行）有显著的时间效率优势。

2.3 Plan-and-Execute的状态机形式化

$$M_{\text{PE}} = (Q_{\text{PE}}, \Sigma_{\text{PE}}, \delta_{\text{PE}}, q_0, F_{\text{PE}})$$

符号 定义
$Q_{\text{PE}}$ ${q_{\text{plan}}, q_{\text{execute}}, q_{\text{replan}}, q_{\text{finish}}, q_{\text{error}}}$
$q_0$ $q_{\text{plan}}$
$F_{\text{PE}}$ ${q_{\text{finish}}, q_{\text{error}}}$

状态转移表：

当前状态 输入 下一状态 输出
$q_{\text{plan}}$ task $q_{\text{execute}}$ 计划DAG $P=(V,E)$
$q_{\text{execute}}$ step_success $q_{\text{execute}}$ 执行下一可执行步骤
$q_{\text{execute}}$ all_done $q_{\text{finish}}$ 最终答案
$q_{\text{execute}}$ step_failure $q_{\text{replan}}$ 失败步骤信息
$q_{\text{replan}}$ new_plan $q_{\text{execute}}$ 修订后的计划
$q_{\text{replan}}$ replan_failed $q_{\text{error}}$ 错误终止

2.4 重规划机制

【应当理解】 Plan-and-Execute的关键工程难点是：何时触发重规划？

重规划触发条件：

触发条件 检测方法 重规划策略
步骤执行失败 工具返回错误/超时 修订失败步骤及依赖步骤
计划过时 执行结果与预期不符 基于已获得的信息重新规划
新信息出现 执行中发现计划外的重要信息 扩展计划，增加新步骤
步骤数超限 执行步数超过预算 压缩剩余计划

重规划的代价：每次重规划都需要一次完整的LLM调用（重新生成计划），Token消耗约等于初始规划的消耗。因此频繁重规划会使Plan-and-Execute的Token优势消失。

2.5 Token效率对比：Plan-and-Execute vs ReAct

【必须掌握】 这是选择推理模式的核心量化依据。

ReAct的Token消耗（N步任务）：

$$T_{\text{ReAct}} = T_{system} + T_{user} + \sum_{i=1}^{N} (T_{thought_i} + T_{action_i} + T_{obs_i})$$

由于上下文累积，第 $i$ 步的输入Token还包括前 $i-1$ 步的全部历史：

$$T_{\text{ReAct_input}}(i) = T_{system} + T_{user} + \sum_{j=1}^{i-1} (T_{thought_j} + T_{action_j} + T_{obs_j})$$

Plan-and-Execute的Token消耗（N步任务）：

$$T_{\text{PE}} = \underbrace{T_{plan}}{\text{规划阶段}} + \sum{i=1}^{N} (T_{action_i} + T_{obs_i})$$

执行阶段每步无需Thought，且上下文只需当前步骤的依赖输入（非全部历史）。

量化对比（10步任务，每步Thought=150, Action=50, Observation=2000）：

模式 规划/推理Token 执行Token(10步) 上下文累积 总Token
ReAct 150×10=1,500 (50+2000)×10=20,500 累积增长 ~132,000
Plan-Execute 800(一次规划) (50+2000)×10=20,500 不累积 ~22,100

关键发现：Plan-and-Execute的Token消耗约为ReAct的 1/6！差距随步数增加而扩大，因为ReAct的上下文累积是 $O(N^2)$ 而Plan-and-Execute是 $O(N)$。

但需注意：Plan-and-Execute的规划质量直接影响执行成功率。如果规划错误，重规划的代价可能抵消Token优势。

2026年前沿——ReWOO模式 $TRAE_REF：ReWOO（Reasoning WithOut Observation）在规划阶段使用占位符，执行阶段并行填充，比ReAct减少约5倍LLM调用。这是Plan-and-Execute思想的极致优化。

三、Reflexion——自我反思闭环

⏱️ 理论推导 20min（本节约5min）

3.1 Reflexion的核心思想

【必须掌握】 Reflexion由Shinn等人于2023年提出 $TRAE_REF，其核心思想是在ReAct循环之外增加一个自我反思层，使Agent能从失败中学习。

Reflexion将Agent的运行分为多个trial（尝试），每个trial是一个完整的ReAct循环。trial结束后，一个评估器（Evaluator）判断结果是否正确，如果错误，Agent生成反思（Reflection）并写入反思记忆（Reflection Memory），下一个trial会读取反思记忆来避免重复错误。

这被称为Verbal Reinforcement Learning（语言强化学习）——用自然语言反思替代传统RL中的数值化奖励信号。

【必须掌握】 这是本课核心知识点之三——反思记忆的数据结构与更新策略。

3.3 Reflexion的状态机形式化

$$M_{\text{Reflexion}} = (Q_{\text{R}}, \Sigma_{\text{R}}, \delta_{\text{R}}, q_0, F_{\text{R}})$$

符号 定义
$Q_{\text{R}}$ ${q_{\text{react}}, q_{\text{evaluate}}, q_{\text{reflect}}, q_{\text{retry}}, q_{\text{finish}}, q_{\text{error}}}$
$q_0$ $q_{\text{react}}$
$F_{\text{R}}$ ${q_{\text{finish}}, q_{\text{error}}}$

状态转移表：

当前状态 输入 下一状态 输出
$q_{\text{react}}$ task + reflection_mem $q_{\text{evaluate}}$ ReAct执行结果
$q_{\text{evaluate}}$ result $q_{\text{finish}}$ / $q_{\text{reflect}}$ 评估通过/失败
$q_{\text{reflect}}$ failure_info $q_{\text{retry}}$ 反思文本写入记忆
$q_{\text{retry}}$ reflection_mem $q_{\text{react}}$ 带反思记忆的新trial
$q_{\text{retry}}$ max_trials $q_{\text{error}}$ 超过最大尝试次数

3.4 反思记忆的更新策略

【必须掌握】 反思记忆的更新策略直接影响Reflexion的收敛性。

策略1：全量保留——保留所有反思

$$\text{Memory}_{t+1} = \text{Memory}_t \cup {r_t}$$

优点：信息完整。缺点：上下文膨胀，后期trial的输入Token过大。

策略2：滑动窗口——只保留最近 $k$ 条反思

$$\text{Memory}_{t+1} = \text{Memory}_t[-k:] \cup {r_t}$$

优点：Token可控。缺点：丢失早期教训，可能重复早期错误。

策略3：重要性加权——按错误频率和严重性排序

$$\text{Memory}_{t+1} = \text{TopK}(\text{Memory}_t \cup {r_t}, \text{score})$$

其中评分函数：

$$\text{score}(r_i) = \alpha \cdot \text{frequency}(r_i) + \beta \cdot \text{severity}(r_i) + \gamma \cdot \text{recency}(r_i)$$

  • $\text{frequency}$：该错误类型出现次数
  • $\text{severity}$：错误严重程度（由Evaluator评定）
  • $\text{recency}$：时间衰减因子 $e^{-\Delta t / \tau}$

三种策略对比：

策略 Token消耗 信息保留 实现复杂度 适用场景
全量保留 $O(N)$ 增长 完整 低 短任务(≤3 trials)
滑动窗口 $O(k)$ 固定 可能丢失 低 中等任务(3-5 trials)
重要性加权 $O(k)$ 固定 智能筛选 高 长任务(5+ trials)

3.5 Reflexion的收敛性分析

【应当理解】 Reflexion不保证收敛——Agent可能在多个错误状态间反复跳转。

收敛条件：每次trial的错误集合严格递减：

$$E_{t+1} \subsetneq E_t$$

即每次反思都消除了至少一种错误类型。这在实践中难以保证，因为：

  1. 修复一个错误可能引入新错误
  2. LLM的随机性导致相同反思可能产生不同行为
  3. 评估器本身可能不准确

工程对策：设置最大trial次数 $T_{max}$（通常3-5次），超过后返回最佳结果而非继续重试。

2026年前沿——MAR（Multi-Agent Reflexion） $TRAE_REF：MAR将Reflexion扩展到多Agent设置，引入多样化推理角色和评判模型，在HotPotQA上比原始Reflexion提升3个百分点。这将在第14课（多Agent系统架构）深入讨论。

四、三种推理模式的状态机形式化对比

⏱️ 理论推导 20min（本节约3min）

4.1 统一状态机框架

【必须掌握】 三种模式可以用一个统一的状态机框架描述，区别在于状态集合和转移函数的不同。

定义统一Agent状态机：

$$M_{\text{Agent}} = (Q, \Sigma, \delta, q_0, F, \mathcal{M})$$

其中 $\mathcal{M}$ 是记忆系统（可选），其余符号同标准DFS定义。

4.2 三种模式的状态转换对比矩阵

维度 ReAct Plan-and-Execute Reflexion
核心状态 think→act→observe plan→execute→(replan) react→evaluate→reflect→retry
循环类型 内循环（单trial内） 内循环（执行步骤间） 外循环（trial间）
记忆系统 无（仅上下文历史） 计划DAG 反思记忆 + 上下文历史
决策频率 每步 规划时一次 + 重规划时 每trial + 每步(内循环ReAct)
终止条件 finish / max_steps / no-progress all_done / max_steps / replan_failed evaluate_pass / max_trials
Token复杂度 $O(N^2 \cdot \bar{T})$ $O(N \cdot \bar{T})$ + 规划开销 $O(T \cdot N^2 \cdot \bar{T})$
典型失败模式 无限循环 计划过时 自我批判死循环
架构修复 max_steps + 非进展检测 重规划触发器 critic_budget + 超时接受

其中 $N$ 是步数，$T$ 是trial数，$\bar{T}$ 是平均每步Token。

4.3 模式选择决策框架

【必须掌握】 架构设计师需要根据任务特征选择推理模式。

任务特征 推荐模式 理由
短horizon（≤5步）、探索性 ReAct 每步重新决策，适应性强
长horizon（10+步）、结构化 Plan-and-Execute Token效率高，可并行
有可验证的正确性标准 Reflexion 自我纠错提升质量
短horizon + 质量要求高 Reflexion (内含ReAct) 反思提升单次质量
长horizon + 质量要求高 Reflexion (内含Plan-Execute) 规划+反思双保险
交互式对话 ReAct 对话式，每轮重新决策
文档处理流水线 Plan-and-Execute 批量、可并行
代码生成（有测试） Reflexion (内含ReAct) 测试作为Evaluator

架构决策含义：三种模式不是互斥的，而是可组合的。生产级Agent通常采用嵌套结构——外层Reflexion包裹内层ReAct或Plan-and-Execute。第12课（LangGraph）将展示如何用图编程实现这种嵌套。

参考答案

题目1 参考答案

三元组定义：

$$\text{ReAct Step}_t = \langle \text{Thought}_t, \text{Action}_t, \text{Observation}_t \rangle$$

  • Thought_t：第t步的自然语言推理
  • Action_t：第t步的工具调用指令（JSON格式）
  • Observation_t：第t步的工具返回结果

状态机（参见1.2节的状态转移图）：

$M_{\text{ReAct}} = (Q, \Sigma, \delta, q_0, F)$

  • $Q = {q_{\text{think}}, q_{\text{act}}, q_{\text{observe}}, q_{\text{finish}}, q_{\text{error}}}$
  • $q_0 = q_{\text{think}}$
  • $F = {q_{\text{finish}}, q_{\text{error}}}$

关键转移：think→act（生成Action）→observe（获取结果）→think（继续推理）或→finish（任务完成）。任意状态在max_step输入下跳转到error。

常见错误模式：

  • 遗漏error状态和max_step转移——无限循环是ReAct的最大风险
  • 将Observation写为LLM生成而非系统注入——会导致幻觉

题目2 参考答案

ReAct总Token消耗：

ReAct的上下文是累积的，第 $i$ 步的输入包含前 $i-1$ 步的全部历史：

$$T_{\text{ReAct}} = T_{system} + T_{user} + \sum_{i=1}^{10} \left[ T_{thought} + T_{action} + T_{obs} + \sum_{j=1}^{i-1}(T_{thought_j} + T_{action_j} + T_{obs_j}) \right]$$

每步新增Token = 150 + 50 + 2000 = 2200

累积Token = 2000(系统) + Σ(i=1 to 10) [2200 + 2200×(i-1)]
= 2000 + 2200 × (1 + 2 + 3 + … + 10)
= 2000 + 2200 × 55
= 2000 + 121,000
= 123,000 Token

Plan-and-Execute总Token消耗：

$$T_{\text{PE}} = T_{plan} + \sum_{i=1}^{10} (T_{action_i} + T_{obs_i})$$

执行阶段不需要Thought，且不累积历史（每步只需当前依赖输入）：

= 800 + 10 × (50 + 2000)
= 800 + 20,500
= 21,300 Token

对比：ReAct的Token消耗是Plan-and-Execute的 5.8倍。差距来源于：①ReAct每步有Thought（150×10=1500），②ReAct的上下文累积导致 $O(N^2)$ 增长。

题目3 参考答案

Verbal Reinforcement Learning：用自然语言反思替代传统RL中的数值化奖励信号。传统RL通过标量奖励 $r \in \mathbb{R}$ 引导策略更新；Reflexion通过自然语言反思文本 $r \in \text{Text}$ 引导LLM在下一个trial中调整行为。优势是无需训练（零样本）、可解释性强；劣势是无法保证收敛、依赖LLM的理解能力。

三种更新策略：

策略 公式 优点 缺点
全量保留 $\text{Mem}_{t+1} = \text{Mem}_t \cup {r_t}$ 信息完整 Token线性增长
滑动窗口 $\text{Mem}_{t+1} = \text{Mem}_t[-k:] \cup {r_t}$ Token可控 丢失早期教训
重要性加权 $\text{Mem}_{t+1} = \text{TopK}(\text{Mem}_t \cup {r_t}, \text{score})$ 智能筛选 实现复杂

题目4 参考答案

（a）ReAct最大步数：

$$N_{max} = \frac{8192 - 2000 - 200 - 1000}{1200} = \frac{4992}{1200} \approx 4 \text{ 步}$$

（预留1000 Token给回复输出）

4步远小于15步，无法完成任务。

（b）Plan-and-Execute最大步数：

执行阶段每步消耗 = Action(50) + Observation(1000) = 1050 Token（无需Thought）

$$N_{max} = \frac{8192 - 2000 - 200 - 800 - 1000}{1050} = \frac{4192}{1050} \approx 3 \text{ 步}$$

仍然不够（需要15步）。Plan-and-Execute在8K窗口下也无法完成。
