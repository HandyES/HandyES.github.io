一、多Agent的判据与代价（模式对比 Part 1）

1.1 回收第13课伏笔：什么是”真”多Agent系统

第13课指出：OpenManus的PlanningFlow让多个executor轮流干活，本质是时间维调度——任一时刻只有一个Agent在运行，它只是”换了大脑的单Agent”。真多Agent系统是空间维协作：

真多Agent判据：系统中是否存在两个及以上拥有独立上下文窗口的Agent实例同时处于ACTIVE状态（并行运行、可能互相通信）。满足→空间维协作（多Agent）；不满足→时间维调度（多角色单Agent）。

这个判据的意义不是贬低时间维调度——第13课已证明它简单可靠（OpenManus的保守恰是对分布式复杂性的敬畏）。判据的意义是帮你识别自己在建什么：

时间维调度（多角色单Agent） 空间维协作（真多Agent）
同一时刻ACTIVE数 恒为1 ≥2
上下文 共享一条消息历史 每Agent独立窗口（隔离）
需要Handoff协议吗 不需要（函数调用即”交接”） 需要（控制权+上下文转移）
需要死锁检测吗 不需要（无并行等待） 需要（并行等待可能成环）
失败面 单点（LLM一步错） 协调缺陷（MAST：最大根因）

**架构师第一原则：能用时间维调度解决的，绝不上空间维协作。**多Agent是分布式系统——你会继承分布式系统的全部经典问题（通信、状态同步、死锁、部分失败），只是”进程”换成了LLM实例。

既然代价这么大，什么时候值得？2026年行业共识收敛为三个条件（Anthropic工程博客 + 社区讨论）：

典型命中场景（Anthropic研究系统）：深度研究任务——超出单一上下文窗口、需要并行搜索海量来源、需要读-写分工。不命中就别拆：简单任务、上下文能装下、无质量对抗需求——单Agent + 图编排（第12课）是更优解。

二、四种协作模式与形式化对比（模式对比 Part 2）

模式对比15分钟：本节每种模式按”架构图→机制→工程要点→陷阱”四步走，最后给出必须掌握的形式化对比矩阵。

2.1 Supervisor模式：中心化调度与结果聚合

机制：Supervisor接收任务→分解为子任务→按Worker专长路由（任务分配）→收集结果→聚合/决定重做或交付。Worker之间不直接通信，一切经中心——这正是它死锁风险低的原因（见2.5）。

工程要点：

  • 共享状态用结构化工件（dict/JSON），不用自由文本转述——2026年共识：“当多Agent间状态由共享结构化工件而非自由文本handoff管理时，多Agent更可能获得收益”（工件可校验、可版本化、可审计，自由文本会失真）
  • Supervisor要维护全局视图：任务进度、重试预算、终止判定——终止权收归中心（对照第13课”终止权收归框架”的同一思想）
  • 失败处理：Worker失败→中心重试/换人/降级（第05课错误处理FSM在协作层的复用）

Anthropic orchestrator-worker实战经验（官方工程博客，2025-06，仍是2026年行业参考）：

经验 数据/做法
模式形态 lead agent（编排者）+ 3~5个specialized subagents，各自独立上下文窗口+工具子集
并行收益 研究任务墙钟时间缩短约90.2%（内部评测）
token代价 多Agent系统token消耗约为单Agent对话的15倍
任务描述敏感性 提示词的微小变化（”多做研究”vs”用工具”）导致Agent行为剧变——任务描述质量=多Agent质量
上下文压缩 subagent把海量原始检索压缩为关键信息回传lead——结果摘要优于过程转述（衔接第04课压缩策略）
适用边界 大量并行化、超出单上下文窗口、需要复杂工具连接的任务才用多Agent

Proposer-Reviewer：Supervisor的质检特例（grill-me决策D13）。当Supervisor编排”生成者→审核者”两个角色时，就得到PR模式——产出在提交前由独立审核者检查。与第03课Reflexion的对比是本课必须掌握的知识点：

维度 Proposer-Reviewer（前置审核） Reflexion（后置反思，第03课）
触发时机 产出提交前（pre-commit拦截） 任务失败后（post-failure学习）
审核者 独立Agent（独立上下文，无生成者偏见） 生成者自己（自反思）
防住什么 错误产出流入下游（防线内拦截） 同类错误跨任务重演（反思记忆写入）
防不住什么 审核者与生成者共有的系统性盲区（同模型同提示词族→同偏见）；每次产出都付费 第一次失败的代价（已经发生）；自我评价的确认偏差
成本模型 每次产出付审核token 仅失败时付反思token
状态 无状态（每轮独立） 有状态（反思记忆复用，第09课长期记忆）

**关键洞察：两者互补而非互替。**PR挡”新错误进入下游”，Reflexion防”同类错误重演”。生产系统典型叠加：审核驳回的案例自动写入反思记忆库→下次生成者开工前检索历史教训（审核结果反哺生成，闭环）。研究助手的”审核员”节点就是PR模式的项目落点——引用真实性核查（法务合规要求）必须前置拦截，不能等用户投诉后再反思。

陷阱：Supervisor是单点故障（SPOF）；中心成为token瓶颈（所有结果都要过一遍中心上下文）；审核者独立性是买来的——同一LLM+相似提示词的”独立”审核只是半独立（需换模型/换提示词策略强化，或抽检人工）。

2.2 Swarm模式：去中心化与Handoff

机制：没有调度中心，每个Agent自主判断”这个任务归我吗”——归我则处理，不归则handoff给它认为合适的同伴。控制权像接力棒在Agent间传递，系统记住”上一个活跃Agent”（最新消息追加到其上下文）。

工程要点：

  • Handoff协议是命脉——控制权转移+上下文摘要传递必须原子化（第三节专门形式化）
  • 路由知识分布在提示词里：每个Agent的描述（”我是计费专家，退款问题找RefundAgent”）既是能力声明也是路由表——OpenAI Swarm→Agents SDK的心智模型（见下）
  • hop_count必须存在：无中心的代价是”循环交接”无人喊停（A→B→A→…乒乓），只能靠协议自带的跳数上限兜底（第三节）

代表实现（知晓即可）：

  • OpenAI Agents SDK（v0.17.x，2026-06）：Swarm实验（2024-10）的生产级继任者。核心抽象Agent / function tools / handoff延续Swarm，扩展了guardrails（输入输出防护）、tracing（内置追踪）、sessions、hosted tools——handoff心智模型+生产基础设施
  • langgraph-swarm（LangChain官方示例库）：把Swarm实现为LangGraph图——Handoff被建模为节点间转移，复用第12课的checkpoint与流式API
  • 定位认知：Swarm适合对话式流转（客服转接、专家会诊），不适合需要全局规划的深度任务——没有大脑，只有一群专家互相传球

陷阱：循环交接（死锁风险最高的模式）；可观测性差（轨迹分散在各Agent，没有全局trace则无法排障——必须全链路trace_id）；错误方向无人纠正（无监督者，一个错误交接可能把任务带进沟里）。

2.3 Hierarchical模式：层级委派与上报

机制：Supervisor的递归——中层既是下属的Supervisor又是上级的Worker。任务自顶向下委派（每层只管一层抽象），结果自底向上汇聚（每层先聚合再上报）。各层保留层级缓存：中层不必把子树全部细节上报，只上报聚合摘要（信息逐层压缩——对应组织管理学”每位经理只需向上级汇报异常与结论”）。

工程要点：

  • 深度d与分支因子b是核心参数：d大→跨层延迟与语义失真累积（指令传三层，每层”翻译”一次）；b大→单层Supervisor过载（回到2.1的token瓶颈）
  • 中间层是子树的SPOF：L2-a崩溃丢失整棵子树——需要子树级checkpoint（LangGraph子图嵌套，第12课）
  • 职责划分要MECE（互斥完备）：子树间职责重叠→任务在兄弟间被踢皮球（Agent间对齐失败，MAST第三类根因）；有真空→无人认领
  • 代表实现：CrewAI hierarchical process（manager Agent分配Task）、Google ADK嵌套团队结构

陷阱：多样性崩溃（ACL 2026）——层级协调本身就是三层结构耦合之一，深层级+密集通信推动过早共识：”团队”讨论半天不如一个Agent独立思考。规模幻觉：Agent数量≠智能总量，1,642条轨迹里”重复无意义步骤”多发生在层级系统中（多个Agent做同一件事而互不知晓）。

2.4 Event-Driven模式：事件总线驱动（衔接第12课）

机制：第12课已建好事件总线基础设施（异步Agent/事件驱动架构），本课补多Agent视角：Agent不互相调用，只发布事件/订阅事件——检索Agent发paper.found就转身走人，谁消费、何时消费与它无关。协作完全解耦。

与前三种的本质区别：Supervisor/Swarm/Hierarchical传递的是控制权（”该你干了”），Event-Driven传递的是信息（”有新情况了”）。控制流不存在于任何Agent，而存在于事件拓扑中。

工程要点：

  • 优点天花板：组件崩溃天然隔离（队列缓冲）、横向扩容容易（加消费者）、时间解耦（夜间消化白昼事件——第12课定时触发的协作版）
  • 代价地板：无全局视图——“任务何时算完成”需要专门的完成事件汇聚机制（如 saga 协调器或计数器）；事件风暴（无背压时消息量爆炸）；活锁高发（A的事件触发B、B的事件又触发A——回环）
  • 可观测性最佳：事件流天然是全量执行日志（事件溯源——第12课DeltaChannel检查点思想的协作版）
  • 代表实现：AG2事件驱动编排、第12课自建事件总线直接扩展

2.5 形式化对比矩阵【必须掌握】

先做三个维度的形式化推导，再给总矩阵。

（a）拓扑形式化。设协作拓扑为有向图 G=(V,E)，V为Agent集，边表示直接通信/控制关系：

  • Supervisor（星型）：V={s}∪W，|W|=k，|E|=2k（k条task边+k条result边），图直径2
  • Swarm（受限动态图）：任意G，但受不变量约束——同一时刻至多1个ACTIVE节点，实际退化为动态链/环
  • Hierarchical（树）：深度d、平均分支因子b，|V|≈(b^(d+1)−1)/(b−1)，图直径2d
  • Event-Driven（订阅图）：物理星型（总线），逻辑图E=f(订阅关系)随时间变化——拓扑本身是运行时数据

（b）通信复杂度。设k=并发Worker数、R=调度轮数、H=handoff次数、E=事件数、S̄=事件平均订阅者数、d=树深、b=分支因子：

模式 总消息量推导 结果 可预算性
Supervisor 每轮下发k条+回收k条，共R轮：M=2kR O(kR) ✓ 由中心计划决定
Swarm 每次交接1条：M=H O(H)，H无上界 ✗ 取决于运行时决策
Hierarchical 满树下钻+上报：M=2·Σᵢ₌₁ᵈ bⁱ≈2bᵈ O(bᵈ)，跨层延迟O(d) ✓ 由组织结构决定

注意Swarm的”不可预算性”——这是hop_count上界存在的形式化理由：必须人为给H一个上界，否则消息量与token成本双双失控。

（c）容错性形式化。定义SPOF(G)为”移除后控制流中断的节点集”：

  • Supervisor：SPOF={s}——中心崩溃全停；但Worker故障恢复能力最强（中心有全局视图，可重试/换人/降级）
  • Swarm：SPOF=∅（结构上无单点），但当前控制权持有者是逻辑单点——它崩溃则任务卡死
  • Hierarchical：SPOF=全部非叶节点（各对其子树负责）——故障隔离粒度=子树
  • Event-Driven：SPOF=总线本身（消息中间件必须高可用）；组件故障隔离粒度=消费者组

（d）总矩阵（本课核心知识点的浓缩——建议抄进笔记）：

通信复杂度 O(kR) 可预算 O(H) 不可预算 O(bᵈ)+跨层O(d) O(E·S̄)

三、Handoff协议状态机设计【必须掌握】（工程实现 Part 1）

3.1 Handoff的本质：控制权与上下文的原子转移

一次handoff同时转移两样东西：

只传控制权不传上下文→接收者失忆（从头问用户）；只传上下文不传控制权→两个Agent同时活跃（控制权分裂，输出互相冲突）。原子性=两者要么都完成，要么都不发生——这是两阶段设计的根源。

3.2 状态机形式化

为什么要两阶段（HANDOFF→ACK→释放）？若A发出handoff就立刻释放控制权，目标B若拒绝/崩溃/超时，控制权真空——任务无人认领，系统死等。两阶段让A在确认被接受前保持责任，ACK超时则回退自处理。这与数据库两阶段提交(2PC)同构：协调者不能在参与者确认前单方面提交。

Q5 参考答案

①资源分配图：P={Planner,Writer,Reviewer,Data}，R={r1,r2,r3}。请求边：Planner→r2、Writer→r3、Reviewer→r1、Data→r2。分配边：r1→Writer、r2→Reviewer、r3→Data。②wait-for图（请求边指向持有者）：Planner→Reviewer（r2的持有者）、Writer→Data（r3持有者）、Reviewer→Writer（r1持有者）、Data→Reviewer（r2持有者）。共4条边。③三色DFS（字典序起点Planner）：[Planner]灰→[Planner,Reviewer]灰→[Planner,Reviewer,Writer]灰→[Planner,Reviewer,Writer,Data]灰→Data的邻居Reviewer为灰（回边）→环=stack自Reviewer起+[Reviewer]=[Reviewer,Writer,Data,Reviewer]。④死锁集合={Reviewer,Writer,Data}（环上三者互相等待）；Planner是”无辜受害者”——它等待Reviewer，Reviewer在环中导致Planner被连带阻塞，但Planner自身不在环上。⑤牺牲者：选Data（假设其启动最晚/工作量最少——回滚代价最小；且统计工件可由Writer的输入重新生成，属”可重做”资源）。恢复：终止Data→r3释放、Data的wait边清除→Writer获得r3完成写作→释放r1→Reviewer获得r1完成审核→释放r2→Planner与（重新派发的）Data恢复。⑥|P|=4、|E_w|=4→O(4+4)=O(8)——线性于图规模，与环长无关（三元环照样检出，见5.2实验③）。
