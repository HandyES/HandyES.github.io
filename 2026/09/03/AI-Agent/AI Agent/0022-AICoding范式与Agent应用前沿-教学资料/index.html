四、范式概述：从Vibe Coding到Harness Engineer（15min）

4.1 三次范式跃迁（2024-2026）

2024到2026年，AI编程完成了三次范式跃迁。核心判据只有一个：人类角色在哪一层。

（1）L1 Vibe Coding（2024，Andrej Karpathy提出）

零门槛：自然语言描述需求，AI生成代码，”感觉对了”就继续。它的工程缺陷是系统性的：

  • 歧义：说”加一个用户管理功能”，用户是管理员还是终端用户？软删除还是硬删除？Session还是JWT？AI必须做出一个个沉默的决策，猜错的修复成本随系统复杂度指数增长
  • 范围蔓延：无需求边界，AI过度实现或漏掉关键点
  • 幻觉：编造不存在的API
  • 不可审查、不可复现：改一个词prompt，输出完全不同；团队无法在实现前对齐预期
  • 技术债累积：每次”看起来能用”的修补都在积累混乱

正确定位：Vibe Coding是素描不是施工图——快速验证想法、一次性脚本、原型Demo的最优解，不能用于长期维护的生产系统。

（2）L2 Spec Coding（2025）

行业共识转向：”AI Coding效果不好，往往不是因为模型太弱，而是因为人的指令含糊。”解法是把”做什么”与”怎么做”分离——人定义规格，AI按规格实现。

SDD（Spec-Driven Development）标准四步：

步骤 回答 内容 示例（社交登录功能）
Spec 做什么 功能目的/使用场景/需求边界/验收标准，刻意技术无关（产品经理也能看懂） “新用户点Google登录→重定向Dashboard并获得有效Session；已绑定Google的用户用同邮箱GitHub登录→关联到同一档案；取消授权→回到登录页显示友好提示而非白屏”
Plan 怎么做 注入开发者专业判断：技术框架/数据模型/测试策略/性能约束 “NextAuth.js + App Router；JWT存HttpOnly Cookie；User实体新增provider字段；单测覆盖≥90%；登录P99<100ms”
Tasks 分而治之 原子任务：每个可在一次Agent Session完成、产出可验证变更+测试 安装配置→数据模型→登录接口→Session管理→单测→集成验证
Implement AI执行 按任务列表逐个实现，每个任务完成后按Spec验收标准自我验证 —

产业实践（知晓即可）：GitHub开源Spec Kit工具包（/specify → /plan → /tasks命令流水线，模板覆盖Copilot/Claude Code/Gemini CLI/Cursor/Windsurf）；OpenAI Symphony架构要求每个issue绑定SPEC.md作为契约；Claude Code内置Plan Mode（轻量版Spec Coding）；AWS Kiro以规格为核心驱动Agent开发【联网更新v6.7】。

（3）L3 Harness Engineer（2026）

Spec Coding没解决的问题：运行时故障恢复、多Agent编排与状态管理、上下文窗口动态管理、安全防护与人工审批。2026年的答案是Harness——人类不再关注代码实现，专注构建Agent的运行环境：行为边界、运行规则、治理门禁。

关键辨析（本课概念核心）：Harness不是Agent，Harness是管理Agent如何运行的软件系统（”AI Agent的操作系统”）。这正是第1课的顶层框架在AI Coding语境下的表述——模型是CPU，上下文窗口是RAM，Harness是操作系统。

三次跃迁是层叠关系，不是替代关系：快速验证用Vibe，团队长期维护用Spec，生产系统持续演进用Harness——盖房子：Vibe勾勒轮廓，Spec画施工图，Harness建基础设施。

4.2 Spec Coding三铁律

铁律 内容 一句话解释
1. No Spec, No Code 没有规格，不准写代码 歧义在规格层的修复成本远低于代码层
2. Spec is Truth 规格与代码冲突时，错的一定是代码 统一事实源，消除”代码漂移”
3. Reverse Sync 发现Bug，先修规格，再修代码 保证规格长期有效——规格一旦腐烂，整个体系失效

为什么铁律在经济上合理（Code is Cheap, Context is Expensive）：

输入增加但便宜，输出大幅减少——前期的一次性结构化投入，换来的是对话轮次的数量级下降，总成本反而更低、结果还可复现（换模型结果一致）。

4.3 渐进式复杂度管理

来自《人月神话》的核心洞察（第21课知识飞轮的理论根基在此再次出现）：

  • 交易状态机该多复杂还是多复杂——本质复杂度由业务决定，任何工具消除不了它
  • AI Coding方法论能做的：高效应对本质复杂度 + 压缩自身引入的偶然复杂度
  • 评判一个AI编码方案好坏的唯一标准：应对本质复杂度的效率有多高、自身引入的偶然复杂度有多低

渐进式的现实依据：约70%的需求是≤5人日的小需求。改个字段、修个bug也要先写spec再拆tasks？——这就是流程的偶然复杂度在吃掉你的效率。解法是不同复杂度的需求，暴露不同深度的流程：

需求档位 流程深度
小需求（改字段/修bug） 直接做，Rules兜底
中等需求（0.5-2人日） 简版spec.md：变更范围+验收标准
复杂需求（>2人日） 完整流程：spec.md + tasks.md + 两阶段review

三条关键原则：

  1. 简单需求不承担复杂流程的成本
  2. 流程是可选增强，而非强制前提——Rules始终生效，Spec按复杂度加载
  3. 本质：只有本质复杂度够高时，才引入对应重量的流程

4.4 L3 AI Coding概念：成熟度模型与人审重心的迁移

“L3 AI Coding”有两个互相印证的框架，讲的其实是同一件事。

框架一：Software Factory成熟度模型【联网更新v6.7】

层级 名称 人审对象 人机比（Operator Leverage）
L0 Manual 全部代码 N/A
L1 Assisted 每条补全建议 1:1
L2 Copilot 每次多文件变更（commit前审查） 1:1 ~ 1:3
L3 Spec-Driven 规格质量+评估结果，不逐行审代码 1:3 ~ 1:10
L4 Governed Autonomy 治理门禁+异常+升级处理 1:10 ~ 1:50

L3的定义性特征：Agent对着Live Spec（随代码持续演化的活规格）执行，Eval Harness（评估挂具）按机器可读的验收标准自动验证；人的审查对象从代码行上移到规格与评估结果。

框架二：三次范式跃迁的L3（Harness Engineer时代）——见§4.1。

两个”L3”的统一：无论哪个框架，都指向同一个趋势——人类判断力从实现层上移到规格与评估层；验证工作由Eval Harness+CI门禁补位。这与第10课”评估即Agent的单元测试”完全同构：eval不是事后检查，是开发流程本身。

Spec自身的成熟度三级（知晓即可）：Spec-First（先写再编码，用完归档）→ Spec-Anchored（Spec与代码共存仓库、随代码持续演化）→ Spec-as-Source（Spec是主工件，改Spec即改系统）。

4.5 Rules + Spec + Skills 三位一体

渐进式Spec框架的完整目录结构（一个可直接抄的生产级布局）：

三位一体的本质是知识的三种存在形态——这正是第4课上下文工程+第9课记忆分层的开发场景实例化：

组件 加载时机 记忆系统对应 成本特性
Rules 始终生效 系统提示词/宪法 常量成本，压一切场景的偶然复杂度
Spec 按变更加载 情景记忆（当前任务） 按需成本，只在高复杂度时引入
Skills 按需检索 长期知识（索引+正文） 触发式成本，第4课Agent Skills标准

4.6 AI流水线与知识飞轮

标准工作流四阶段（Propose → Apply → Review → Archive，另有Fix与Debug两个修正入口）：

Propose（提案）——人主导，AI辅助

  1. Research：分析代码现状，每个结论必须有出处（文件路径+类名/方法名），不接受空口结论
  2. 逐个提问：一次只问一个问题，优先给2-3个选项+推荐；同时做YAGNI裁剪（识别nice-to-have建议延后）
  3. 分段生成文档，每段确认——越早发现方向偏差，修正成本越低
  4. HARD-GATE：待澄清项全部清零+用户显式确认前，禁止任何编码动作

Apply（执行）——AI主导，人审查

  • 逐步执行（完成一个task→报告→确认）、批量执行、紧急停车（逻辑冲突→立即停止→Reverse Sync）
  • 零偏差原则：Plan是合同，AI是打印机
  • Verification铁律：每个task完成后必须展示可验证证据（编译输出/测试输出/调用结果），禁止”应该没问题”
  • 实时知识采集：每个task完成后立即检查是否踩坑，有则写入log.md

Review（审查）——两阶段Sub Agent（上下文与实现者隔离）

  1. 阶段一Spec Compliance（spec-reviewer）：逐条比对规格与实际代码，核心原则**”不信报告只信代码”**
  2. 阶段二Code Quality（code-quality-reviewer）：基于rules/检查规范、安全红线、异常处理，按Critical/Important/Minor分级
  3. 阶段一PASS才启动阶段二；任一FAIL回到Fix

Archive（归档）——知识沉淀

逐条展示log.md中的知识发现，确认后沉淀到knowledge/，变更目录移入archives/。

知识飞轮（第21课进化闭环的团队版）：

对照第21课的映射关系：学习信号从badcase变成踩坑记录；更新载体从四载体收敛为rules/knowledge/templates；灰度发布变成Git分支+审查门禁。同一套进化闭环理论，在团队开发场景换了一身衣服。

配套的Git规范（安全设计的典范，§6.2会回收）：

  1. 禁止master分支变更（编码前检查当前分支）
  2. 一个task一个commit，自动commit但commit前必须编译通过
  3. 禁止自动push——push由人主动触发，保留审查机会

五、工具全景：能力边界与选型维度（10min）

5.1 编排层+执行层两层架构

实践中单一工具很难同时满足”强模型做决策”和”安全模型写代码”，最终演化出两层架构：

为什么分层：全程用顶级模型太贵，全程用便宜模型决策质量不够——关注点分离+成本质量平衡。这是第14课Planner-Worker、第20课Planner-Worker混部第三次在本课程出现：同一个架构模式（强模型规划+轻模型执行），在多Agent系统、推理集群、开发工具三个场景反复重现——这本身就是架构模式泛用性的最好证据。

5.2 四大工具能力边界（2026-09快照）【联网更新v6.7】

架构师读法（三选型认知，比工具本身更重要）：

  1. AutoGen的启示——框架是易变层，协议是稳定层：AutoGen→MAF的交接中，MCP与A2A被原生支持。第11-15课的判断再次被验证：把业务逻辑挂在协议抽象上（MCP工具服务器、A2A互操作），框架只作可替换实现。评估任何框架，先看它对稳定协议的兼容性，而不是功能清单。
  2. 编码工具的收敛趋势：四类产品都在向同一组能力收敛——Skills开放标准（SKILL.md）、Subagent、自主模式、Spec命令（Trae的/spec、Spec Kit的/specify）。AI Coding正在把本课§4的范式变成产品标配。
  3. 模型能力≠产品能力：SWE-bench Verified（2026-09）上，裸模型Claude Opus 5约96%，但产品化Agent如Cline（Sonnet 4.6）约59.8%、Devin 2.0约45.8%【联网更新v6.7】。模型解决”写得对”，产品还要解决”跑得稳”（Harness）——选型时看产品Agent在真实基准上的数字，不要看裸模型宣传数字。

5.3 选型维度：透明度是底线

透明度不是奢侈品，是基础需求——四条硬底线：

  1. 模型型号+版本可见
  2. 完整context可查
  3. 原始输出不被篡改
  4. token用量透明

原因：在不透明的工具上优化prompt和框架，效果无法归因、无法复现；切到透明工具链后，每次调优都能看到效果，迭代速度指数级提升。

6.3 审查闭环的状态机模型

把§4.6的两阶段审查+HARD-GATE+Fix循环合起来，就是审查闭环状态机：

七个状态：IDLE（空闲）→ PROPOSING（提案：Research+逐段确认）→ APPLYING（执行：按tasks逐步+证据展示）→ REVIEW_SPEC（阶段一：规格合规，”不信报告只信代码”）→ REVIEW_QUALITY（阶段二：质量分级Critical/Important/Minor）→ FIXING（修正：增量+文档同步铁律）→ ARCHIVED（归档+知识沉淀）。

架构师读法（三条）：

  1. 状态机的价值不在图好看，在于”非法转移被拦截”——HARD-GATE不是提示词里写”请不要直接编码”（AI可能违反），而是状态机里IDLE/PROPOSING状态根本不存在通往编码的转移边（结构上到不了）。这是”约束靠框架不靠自觉”（第1课Harness约束功能）的精确实现。
  2. 与第21课灰度状态机同构：阶梯/守护指标/回滚 ≈ 两阶段审查/FAIL阈值/FIXING循环——同一个”安全变更”模式在不同领域的投影。
  3. 与第12课LangGraph对照：这本质是一张带条件边的状态图，LangGraph的checkpointing正是这类状态机的框架化实现（中断恢复=断点续审）。

6.4 项目线收官之问：研究助手需要”代码分析”能力模块吗？

这是项目线的最后一个架构决策。用第21课ROI框架完整走一遍：

支持方论证：

  • 研究对象常含代码：arXiv论文的配套实现、GitHub仓库是研究素材的一部分；能读代码的综述Agent可以验证”论文声称的实现复杂度”
  • 第21课§7.2的架构可直接复用（文件系统外部记忆+按需读取）

反对方论证：

  • 能力半径膨胀：代码分析需要专用工具链（grep/AST解析/沙箱执行），每个工具都是攻击面（第21课OWASP rogue agent路径）+维护成本
  • 用户画像错配：研究助手的用户是研究者不是工程师；”分析代码库”属低频需求
  • ROI为负：低频需求×高载体成本（程序载体：开发+验证+回归风险全是最贵的档位，第21课§5.2四载体六维矩阵）

决策建议（分层方案）：

层 方案 理由
默认 不内建代码分析模块 核心能力守恒：能力边界是设计出来的，不是堆出来的
执行态 通过MCP外挂代码分析工具服务器（第11课模式），按需启用 能力可插拔，用进废退，攻击面按需暴露
报告态 检索结果关联GitHub仓库元信息（star数/语言/最近活跃度），不做深度分析 “知晓级”能力：零工具链成本，覆盖80%真实需求

这个决策本身示范了L3 AI Coding的核心思想：研究助手的能力边界，就是它的Harness设计——不给的工具就是没有的能力，边界是刻意的架构选择而非能力不足。

八、参考答案

A1（基础-三铁律）

  1. No Spec, No Code——歧义在规格层的修复成本远低于代码层（改一段文字vs改一堆代码+回归测试）；
  2. Spec is Truth——统一事实源消除代码漂移；两套事实源的仲裁成本远高于维护一套规格；
  3. Reverse Sync——规格一旦腐烂整个体系失效，先修规格保证长期资产不贬值。
    经济学共性：Spec是一次性高质量输入，替代的是约20轮试错中反复重放的上下文——Code is Cheap, Context is Expensive。

A2（基础-复杂度理论）

依据是《人月神话》的复杂度二分：本质复杂度（业务逻辑本身，不可消除）+ 偶然复杂度（工具/流程引入的负担，应该消除）。数据支撑的关键原则是”流程是可选增强，而非强制前提“：既然70%需求是小需求，让它们承担重流程，等于让流程的偶然复杂度吃掉需求本身的价值；Rules（常量成本）兜底一切，Spec（按需成本）只在高本质复杂度时加载。

A3（基础-成熟度模型）

L2人审多文件代码变更本身（commit前逐处看diff）；L3人审规格质量与评估结果，不逐行审代码——由Live Spec+Eval Harness按机器可读验收标准自动验证。人机比从1:11:3提升到1:31:10。本质：人类判断力从实现层上移到规格与评估层。

B4（分析-成本估算）

Vibe路径：对话约20轮，第k轮需重放前k-1轮全部历史，总Token ≈ Σᵢ₌₁²⁰(前缀ᵢ) ——随轮数二次增长；且结果不可复现（换措辞重来）。Spec路径：写Spec是一次性投入（人时+一次性Token），之后3-5轮收敛，每轮上下文=Spec+当前Task（近似常量）；且同一Spec换模型结果一致。结论：一次性结构化投入换来轮次数量级下降+复现性，省钱的同时还提高了质量下限——Spec中的验收标准本身就是测试计划。

B5（分析-框架vs协议）

启示：框架是易变层，协议是稳定层。AutoGen→MAF交接中MCP/A2A被原生支持，说明协议作为事实标准存活于框架更替之上。选型动作：①业务逻辑挂在协议抽象上（工具做成MCP Server、互操作走A2A），框架只作可替换实现；②评估框架先看它对稳定协议的兼容性，而非功能清单；③警惕框架锁定——AutoGen用户的迁移成本，正是”把逻辑写死在框架API里”的代价。

B6（分析-流程误用）

问题：把偶然复杂度当成本质复杂度处理——70%的小需求走全流程，流程成本超过需求本身价值，团队必然阳奉阴违（私下跳流程），规范失效。修正：①三档分级——小需求直接做（Rules兜底）/中等简版spec.md/复杂需求全流程；②分级判据事先写进rules/（如人日估算、变更风险等级），消除”该走哪档”的争议；③用数据校准——统计跳流程导致的返工率，动态调整档位阈值。

C7（设计题-参考方案）

工具清单（最小3个）：

工具 输入 输出（证据设计）
repo_overview 仓库URL或本地路径 语言构成/目录树/star数/最近commit——每项附来源（API端点或文件路径）
code_search 查询词+路径过滤 匹配片段+文件名:行号（可溯源，供综述引用）
method_digest 文件路径 函数签名列表+调用关系摘要（静态分析，不执行）

安全边界：①只读挂载（无写权限）；②网络白名单仅限代码托管平台raw域；③每工具调用30s超时；④输出截断（防上下文炸弹，第4课）；⑤静态分析为主，不执行任意代码（如必须执行→独立沙箱容器+无网络）。

降级方案：完整版=在线拉取仓库全量分析；降级版=用户上传zip+本地静态解析；最小版=仅repo元信息API（无代码内容）。

评分要点：证据设计（来源可溯）/最小权限/超时与截断/降级完整/工具粒度合理。

C8（设计题-参考方案）

状态：IDLE → COLLECTING（检索）→ OUTLINING（大纲）→ WRITING（撰写）→ REVIEW_CITATION（引文核验）→ REVIEW_QUALITY（事实一致性）→ DELIVERED；修正态FIXING。

事件与拦截（转移表节选）：

当前状态 事件 下一状态
IDLE query COLLECTING
COLLECTING sources_ready OUTLINING
OUTLINING outline_confirmed WRITING
WRITING draft_done REVIEW_CITATION
REVIEW_CITATION pass REVIEW_QUALITY
REVIEW_CITATION fail FIXING
REVIEW_QUALITY pass DELIVERED
REVIEW_QUALITY fail FIXING
FIXING fixed REVIEW_CITATION

HARD-GATE设计（结构性不可达）：①大纲未经用户确认，WRITING不可达（对应”待澄清清零”——研究意图未锁定就写作=沉默决策）；②引文核验未通过，DELIVERED不可达（每个引用必须溯源到真实来源，防幻觉引用——第10课LLM-as-a-Judge+引文验证器补位）；③来源数低于阈值（如<5篇核心文献），OUTLINING不可达。

与第10课评估体系的关系：REVIEW_CITATION/REVIEW_QUALITY两个审查态正是评估体系的状态机化——eval不再是”交付后打分”，而是闭环中的强制状态（不过就不放行）；FIXING→重新审查即”评估驱动的修正循环”。这与§6.3完全同构：HARD-GATE≈Spec确认门，REVIEW≈两阶段审查，FIXING≈增量修正。

评分要点：状态完整性/门禁的结构性设计（非法转移拦截而非提示词劝阻）/失败路径闭环/与评估体系的衔接。
