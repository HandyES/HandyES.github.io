二、本课对"企业级智能研究助手Agent系统"的贡献

第23课修完引擎，毕业答卷里的"推理集群"那一节可以重新签字了。但集群里跑的东西还在变——基座换了、量化工具换了、训练框架的默认值换了。这三件事任意一件变了，第18课那份"部署形态决策文档"就有一半要重写。

本课产出三个项目资产：

  1. 基座候选评分卡——六个新权重按"许可证 / 原生精度 / 引擎要求 / 上下文 / 激活参数"五维打分，直接给研究助手做替换决策（§5.7）
  2. 量化工具链迁移清单——把 AutoAWQ 时代的脚本迁到 llm-compressor，含四个破坏性变更的替换写法（§6.5）
  3. 训练配置默认值 diff 表——三个 TRL 默认值变更 + 一个会 raise 的组合，进 CI 的训练前检查（§7.4）

本课最刺眼的一条：旧文写"v1.12.0 是误发布的烧毁版本，下一真实版本为 v1.13.0"。这句话在 2026-09-13 写下时看起来没问题——但 v1.13.0 实际发布于 2026-09-10，比快照早三天。也就是说，作者查的时候 1.13.0 已经在 PyPI 上了，只是他没刷新页面。这不是知识错误，是流程错误：快照没有记录"查询时刻"。

三、开篇：为什么"权重账"比"引擎账"更难对

推理引擎的账好对——两个引擎，四个 release，纯文本 diff。

模型栈的账难对，原因有三个：

  1. 权重来自几十个仓库。Hugging Face 上 archived: false 且 lastModified 在窗口内的模型有上万条，没有"release notes"这回事。
  2. "最新"不等于"可用"。一个 1T 总参 / 52B 激活的模型发出来了，但 vLLM 要 0.32+、显存要 1.06TB、许可证是 other——它对你的意义可能只是"知道它存在"。
  3. 工具链的默认值是隐式的。你不会去读 llm-compressor 的每一个 default，但那些 default 决定你产出的 artifact 能不能被引擎加载。

所以本课的组织方式不是"按仓库"，而是按决策：

一个先给的判断标准：

权重侧的变更，只有当它改变"能不能部署"（许可证/精度/引擎版本）或"部署成什么样"（激活参数/上下文/量化路径）时，才需要改架构文档。 单纯"涨点"属于评测问题，不属于架构问题。

四、先把基线修对（必须掌握，8min）

4.1 三条独立的基线偏差

我们对 2026-09-13 那份快照做了反向核查：

项目 快照写的 当日实际 偏差性质
TRL v1.11.0，且称"下一真实版本 v1.13.0" v1.13.0 已于 2026-09-10 发布 表述在写下 3 天后即失效（实为已发布）
transformers v5.15.x v5.17.0 已于 2026-09-09 发布 落后 1 个 minor，4 天
量化默认工具 "AWQ 是 INT4 默认" vLLM 文档已挂 ⚠️ AutoAWQ deprecated 归属错误（算法 vs 工具）

第三条值得单开一节（§6.1），因为它是概念混淆而不是版本落后：AWQ 是算法，AutoAWQ 是实现该算法的工具。算法没死，工具被 llm-compressor 接管了。把这两者混为一谈，会导致"换工具时把算法也换掉"的错误决策。

4.3 一条可以用来判断"该不该跟"的经验法则

把上表按 minor 数量排序，会看到一个规律：

  • transformers / TRL 这两个"平台型"组件，minor 数最多（7 和 6）——因为它们同时承载 tokenizer、权重加载、训练循环，迭代面最广。
  • PEFT / ONNX Runtime 这类"窄职责"组件，minor 数最少（1 和 2）——职责窄，接口稳定。

法则：跟进成本 ≈ minor 数 × 接口暴露面。所以研究助手这种"自己写业务、用框架做训练"的项目，策略应该是：

这一节不写"谁更强"，只写"它改变了什么约束"。因为对架构师来说，一个模型的价值不在榜首分数，而在"它逼你改哪一行配置"。

5.1 Mistral Large 4（1T-A52B）

维度 事实
仓库 mistralai/Mistral-Large-4-1T-A52B
参数 1T 总参 / 52B 激活
专家结构 128 routed experts，每 token 激活 4 + 1 shared
上下文 1M
体积 54 分片，约 1.06 TB
原生精度 FP8
引擎要求 vLLM 0.32+
许可证 other（非标准开源许可）

约束含义：

  • 1.06TB 的权重单机放不下，必须多机 TP/EP；这不是"选型"，是"部署形态被权重体积决定"。
  • 128 experts 激活 5 个 → 专家并行（EP）不是可选优化，是必需项。EP 的通信模式与 TP 完全不同，第20课的"卡间怎么连"那一节要重算。
  • 原生 FP8 → 省掉一次量化转换，但也意味着你无法用 BF16 做精度基线对比（没有 BF16 checkpoint）。
  • 许可证 other → 商用前必须过法务，这一条在评分卡里是一票否决项。

5.2 Muse Spark Open（816B-A42B）

  • 发布：2026-09-15
  • 结构：816B 总参 / 42B 激活
  • 同时提供 BF16 与 NVFP4 两份 checkpoint

约束含义：这是本期唯一一个"官方直接给低精度权重"的案例。它的意义在于：以前"BF16 → 量化"是你的工作，现在厂商替你做了，你只需要验证 NVFP4 版本的质量是否可接受。分工在往上游迁移——这是第18课"压缩优先级"那一节需要补的一条：先看有没有官方低精度版本，再看要不要自己量化。

5.3 Kimi K3.1-Pro

维度 事实
基座 K3，2.8T 总参 / 896 experts，激活 16
精度 MXFP4 权重 / MXFP8 激活
格式 compressed-tensors 8-bit
加载 需 trust_remote_code=True

约束含义：

  • 2.8T 总参是本期最大。896 个专家激活 16 个意味着极高的稀疏比（1.8%），EP 通信成为绝对瓶颈。
  • trust_remote_code=True 是供应链风险的直接体现——你必须在隔离环境里先审代码，再上生产。
  • MXFP4/MXFP8 是 OCP 开放标准，不是 NVIDIA 专属，理论上跨硬件，但实际 kernel 支持要看引擎。

5.4 DeepSeek-V4.1-Flash-1017

  • 发布：2026-10-17
  • 许可证：MIT（本期唯一真正宽松的）
  • 精度：fp8
  • 模态：多模态

约束含义：MIT + fp8 + 多模态，这三个组合让它成为研究助手最现实的替换候选——许可证不设卡、精度不用转、多模态直接接第10课的多模态 RAG。评分卡里它应该拿最高分（§5.7）。

5.5 Reflection Beam-1.0-501B-A23B

  • 发布：2026-10-07
  • 501B 总参 / 23B 激活
  • 许可证：Apache-2.0

约束含义：Apache-2.0 + 23B 激活，是"中等规模 + 完全可商用"的甜点位。它比 Mistral Large 4 小一半，单机多卡（8×H200）就能跑，不需要跨机。对研究助手这种"要能自己部署"的项目，这个形态比 1T 更实用。

5.6 Step-5-Preview

  • 发布：2026-09-20
  • 状态：Preview

约束含义：Preview = 接口可能变、权重可能撤、许可证可能改。教学上它的价值是作为一个反例：不要在生产路径上依赖 preview 权重，除非你有明确的替换计划。

把五维打分（1-5 分，许可证与引擎要求为一票否决项）：

模型 许可证 原生精度 引擎要求 上下文 激活参数（越小越易部署） 总分 判定
DeepSeek-V4.1-Flash 5（MIT） 5（fp8） 4 4 5（Flash 级） 23 ✅ 首选
Reflection Beam-1.0 5（Apache-2.0） 4 4 4 4（23B） 21 ✅ 次选
Muse Spark Open 3 5（双checkpoint） 3 4 3（42B） 18 ⚠️ 需评估 NVFP4 质量
Kimi K3.1-Pro 2 3 2（trust_remote_code） 5 4（2.8T/16 激活） 16 ❌ 现阶段不适用
Step-5-Preview 2 3 3 3 3 14 ❌ Preview 不进生产
Mistral Large 4 1（other） 3 2（0.32+，1.06TB） 5（1M） 2（52B） 13 ❌ 法务一票否决

上表的"原生精度"维度规则是"是否原生低精度已给"：给了（native_fp8=1）记 5 分；没给但许可证宽松（MIT/Apache-2.0，说明可以自由转换）记 4 分；其余记 3 分。Kimi K3.1-Pro 虽然给了 MXFP4，但它同时要求 trust_remote_code，"给了低精度"这个便利被供应链风险抵消，故按 3 分计——评分卡的规则必须能表达这种抵消，否则就成了数格子。

读表方式：

  • Mistral Large 4 的"1M 上下文"是全场最高分，但许可证一票否决——这正是评分卡存在的意义：防止"被某个亮眼指标带走"。
  • Kimi K3.1-Pro 的 2.8T 在评测上可能最强，但"激活 16/896 + trust_remote_code"两项直接把它挡在生产之外。榜单第一不等于可部署第一。
  • Muse Spark 的 18 分里有 5 分来自"官方双 checkpoint"——这是本期新出现的一个加分维度，旧评分卡里没有。

六、量化：默认工具换人了（必须掌握，20min）

6.1 AWQ 是算法，AutoAWQ 是工具——这两件事必须分开

vLLM 文档现在挂着 ⚠️ AutoAWQ deprecated，量化入口交给 llm-compressor。正确理解是：

AWQ 仍然是 W4A16 的主力算法（它的激活感知缩放思路没有任何替代方案），但"用哪个工具产出 AWQ 权重"已经从 AutoAWQ 换成 llm-compressor。

这个区分为什么重要：如果你的团队文档写"我们用 AWQ"，新人会去装 autoawq，然后发现它和 transformers 5.22 不兼容——而正确做法是用 llm-compressor 产出 compressed-tensors 格式的 AWQ 权重，再由 vLLM 加载。

6.2 格式格局：NVFP4 成为第二默认

格式 定位（2026-11） 变化
FP8（E4M3） 服务端首选，Hopper/Blackwell 甜点位 未变
NVFP4 FP8 之外的第二默认，Blackwell SM100 专属 升级（从"实验"到"默认之一"）
MXFP4 OCP 标准，跨硬件 上升（Kimi K3.1 首发用）
AWQ（W4A16） 精度与吞吐的平衡点 算法仍主力，工具已换
GPTQ "复用社区 artifact" 定位未变
GGUF CPU / Apple Silicon / 端侧 唯一选择，未变

一个具体数据：GLM-5.3 用 MXFP4×FP8 混合，把 1507GB 压到 415GB（−72%），平均 4.5 bits/参数。这个数字是"低精度不是只能救显存、还能救部署形态"的最好证据——1507GB 需要跨机，415GB 单机 8 卡就够。

另一条要更新的判断：AWQ 已经不再承担"新模型首发格式"的角色。新模型出来时，首发支持的通常是 FP8 或 NVFP4，AWQ 往往要等社区补 artifact。所以"AWQ 优先"这个默认策略，在追新模型时要反过来。

6.3 两个新方法：HIGGS 与 QAD

llm-compressor 0.15.0（10-28）新增两个方法：

HIGGS（逐层混合精度）

  • 思路：不同层对量化的敏感度不同，给每层分配不同的 bit 宽度，而不是全局一刀切。
  • 关键数字：标定 <10 秒；6.0-bit 下 WikiText PPL 11.05 / 10.99。
  • 为什么重要：以前的混合精度要跑搜索（几十分钟到几小时），HIGGS 把标定压到 10 秒内，使"每个模型都做一次混合精度"从奢侈变成默认。

QAD（block-wise 量化感知蒸馏）

  • 思路：量化不是"压缩完就完"，而是"压缩后用一个 teacher 把掉下来的精度蒸馏回来"，按 block 做。
  • 与第18课的关系：第18课讲"量化 → 蒸馏两段式，顺序不可换"，QAD 把这个两段式合并进同一个流程，但本质上仍是"先降精度、再用蒸馏补"。

另两个配套能力：

  • REAP 可以直接剪 safetensors，并输出 per-expert saliency（对 MoE 剪枝很关键——896 个专家里哪些能删）。
  • 压缩矩阵新增 MXFP6A8 / MXFP6A16。

6.4 vLLM 侧的四个破坏性变更

这是"换了工具之后仍然会踩"的部分：

变更 影响
fp_quant 与 QuTLASS 后端移除 用到该后端的配置直接失效
Marlin 不再把激活量化到 INT8/FP8，VLLM_MARLIN_INPUT_DTYPE 删除 之前靠这个环境变量调优的，行为会静默变化（不报错！）
W4A8 改走 humming + VLLM_HUMMING_INPUT_QUANT_CONFIG W4A8 的配置写法全变
新增 --linear-backend / linear_backend_per_quant 新增能力，但默认值会决定你实际走哪条 kernel

VLLM_MARLIN_INPUT_DTYPE 删除这一条最危险——因为它不报错，只是"不再生效"。你的服务会正常启动、正常返回，只是速度或精度和你以为的不一样。这类"静默失效"是升级中最难查的一类问题，也是第23课"九问"第 2 问（默认值 diff）的又一个实例。

6.5 迁移清单：AutoAWQ 脚本 → llm-compressor

四个必须记住的差异：

  1. 没有 quant_config 字典了，改成 scheme="W4A16" 字符串
  2. 必须给标定数据集（AutoAWQ 也给了，但 llm-compressor 对样本数更敏感）
  3. 产出是 compressed-tensors 格式，不是 AutoAWQ 的私有格式——好处是 vLLM 直接认，坏处是老工具链读不了
  4. ignore=["lm_head"] 要显式写，否则 lm_head 也会被量化，精度掉得莫名其妙

6.6 落回项目：研究助手的量化决策树

一条红线：llm-compressor 0.15.0 的上界仍是 transformers 5.21.0，而主线已到 5.22.2。所以不能说"transformers 5.22 已被量化工具链验证"——这是一个真实的版本缝隙，写文档时必须留白，不能想当然。

七、TRL：三个默认值，其中一个会直接 raise（必须掌握，12min）

7.1 三个默认值变更

版本 变更 后果
v1.17.0 GRPO 会直接 raise：vLLM importance sampling 默认开启时，若 top_p < 1.0 且未设 top_k > 0 训练直接崩，不是降级
v1.17.0 AsyncGRPO 默认 score_centering=True、importance_sampling_min/max = 0.5/5.0 FP8 sampler 下 reward 从 0.60 掉到 0.34/0.10；改后回到 0.72，代价 15–20% 吞吐
v1.15.0 fused LM head 默认开启 可训长度大幅提升，但 PEFT adapter 要改

第一条最需要单独讲，因为它是从"行为变化"升级到"直接失败"——以前升级最多是效果变差，现在是不让你跑。这种变更的应对方式不是"调参"，而是"先读 release notes 再写 config"。

第二条是个极好的教学案例：默认值 + 硬件特性（FP8 sampler）耦合。同一条默认值，在 BF16 sampler 下无害，在 FP8 sampler 下把 reward 打到 0.10。这说明"默认值是否安全"依赖于你的硬件/精度路径，不是全局常量。

7.2 fused LM head 的收益与代价

v1.15.0 让 fused LM head 默认开启，具体数字：

场景 可训长度（前 → 后） 倍数
gemma-3-1b（262k 词表）DPO 10,240 → 59,392 5.80×
GRPO 28,672 → 114,688 4.00×
8192 tokens 峰值显存 — 降 52–82%

代价（破坏性）：如果 PEFT adapter 要挂到 lm_head 上，必须写 modules_to_save=["lm_head"]，否则 adapter 不会生效——又一个"不报错但错误"的坑。

为什么 fused LM head 这么猛：LM head 是 hidden_dim × vocab_size 的矩阵乘，词表 262k 时这个矩阵极大；fused 实现把"算 logits"和"算 loss"合并，避免物化完整 logits 张量。这就是为什么收益与词表大小正相关——词表越大，省的越多。这也解释了为什么小词表模型（如 32k 词表）几乎看不到收益。

7.3 trainer 清洗：一个可预测的规律

窗口内被移除的 trainer：

版本 被移除
1.13.0 PPO
1.15.0 MiniLLM
1.16.0 SSD
1.17.0 TPO

规律很清楚：TRL 在收缩到"经过验证的主流路径"。PPO 被 GRPO 系替代、MiniLLM/SSD/TPO 这些偏研究的蒸馏变体被清出主线。教学含义：不要把课程锚定在某个具体 trainer 上，要锚定在方法族上（"策略梯度 + 组相对基线"而不是"GRPOTrainer"）。

7.4 训练前检查清单（进 CI）

第 5 条就是 §6.6 那条红线的落地检查——训练环境和量化环境用不同 transformers 版本，是这个生态里最常见的隐性故障源。

八、生态碎片化：pin 冲突是常态（应当理解，5min）

最典型的一个证据：

  • verl v0.9.1（2026-09-20）把 transformers pin 到 5.9.0
  • 而 transformers 主线已经是 5.22.2
  • 相隔 13 个 minor

为什么会出现这种事：verl 依赖 vLLM 的内部接口，而 vLLM 对 transformers 的版本有硬要求；于是 verl 只能把自己的 transformers 固定在"最后一个能配合当前 vLLM 的版本"。这是"框架依赖引擎、引擎依赖平台库"三层耦合的必然结果。

同一版本里也有好消息：verl 的 delta_sharded 权重同步从 34.26s 降到 3.34s（10.3×）。这说明框架在工程效率上仍在大步前进，只是被版本约束卡住了。

架构含义：你的训练环境与推理环境很可能必须使用不同的 transformers 版本。所以：

三个镜像、三个版本、互不兼容。这不是设计失误，这是当前生态的真实形态。把它写进架构文档，比假装"统一版本"要诚实得多。

9.2 第二层：改一个参数看结论怎么变

把脚本A 的"许可证"权重乘 2（w=1 → w=2，模拟法务特别严格的团队），实测结果：

模型 w=1 总分 w=2 总分 增量 排名变化
DeepSeek-V4.1-Flash 23 28 +5 1 → 1
Reflection Beam-1.0 21 26 +5 2 → 2
Muse Spark Open 18 21 +3 3 → 3
Kimi K3.1-Pro 16 18 +2 4 → 4
Step-5-Preview 14 16 +2 5 → 5
Mistral Large 4 13 14 +1 6 → 6

这个结果比"排名会变"更有教学价值：调权重并没有改变排名。原因很直接——许可证分已经被算进总分了，乘 2 只是等比放大差距，而排名的相邻间距足以吸收这个放大。DeepSeek 与 Beam 之间差 2 分，两者许可证都是 5，同增 5 分，差距不变。

真正会改变排名的不是"调权重"，而是改维度集合：比如把"是否有官方低精度 checkpoint"从加分项升为独立维度，Muse Spark 会从 18 跳到 23 附近，与 DeepSeek 持平。所以：

评分卡的"权重"往往是伪参数，"维度"才是真参数。 想让结论变，先问"我漏了哪个维度"，而不是"该给许可证打几分"。

这条也解释了为什么 §5.7 的表里 Muse Spark 明明双 checkpoint 却是 18 分——它拿的那 5 分（precision）只比默认的 3 分高 2，而"双 checkpoint"这件事的真实价值远不止 2 分。评分卡永远会低估它没有建模的维度。

十一、参考答案

A1（基础-算法vs工具）

AWQ 是"激活感知的权重量化"算法（保护显著通道），AutoAWQ 是实现它的一个库。vLLM 文档标记 AutoAWQ deprecated，是指"不再推荐用这个库产出权重"，量化入口交给 llm-compressor。算法本身仍是 W4A16 的主流，只是产出格式从 AutoAWQ 私有格式变为 compressed-tensors。常见错误：以为要换成 GPTQ 或 NVFP4——不必要，AWQ 权重仍可产出，只是换工具。

A2（基础-fused LM head）

LM head 是 hidden × vocab 的矩阵乘，fused 实现避免物化完整 logits。收益与词表大小近似线性：gemma-3-1b 的 262k 词表带来 5.80× 可训长度提升；32k 词表的 logits 张量小 8 倍，省下的绝对显存有限，所以相对收益不显著。

A3（基础-TRL raise）

v1.17.0：vLLM importance sampling 默认开启时，若 top_p < 1.0 且未设 top_k > 0，GRPO 直接 raise。原因大概是采样分布与重要性权重估计在该组合下不自洽（这是行为层面的解释，具体实现细节需读源码）。修复：设 top_k > 0（如 20），或关闭 importance sampling。

B4（分析-四条否决）

①许可证受限（restricted）；②引擎要求 trust_remote_code=True（供应链风险，需代码审计）；③2.8T 总参 / 896 experts 激活 16，EP 通信成为绝对瓶颈，单机放不下、跨机带宽要求极高；④MXFP4 权重 / MXFP8 激活的 kernel 支持面窄，vLLM 侧要 compressed-tensors 8-bit 且版本匹配。加分项：指出"榜单分数高"恰恰是陷阱——它通常来自最大规模的配置，而那正是最难部署的配置。

B5（分析-官方低精度）

它把"量化"从你的工作流里删掉了，只留"质量验证"。例子：Muse Spark Open 同时给 BF16 与 NVFP4 两份 checkpoint；DeepSeek-V4.1-Flash 原生 fp8；Kimi K3.1-Pro 直接 MXFP4/MXFP8。影响：第18课的"压缩优先级"要补一条前置判断——"先问有没有官方低精度版本"。

B6（分析-静默失效）

因为它不产生任何错误：服务正常启动、正常返回、监控指标正常，只是内部 kernel 路径变了，速度和精度与你以为的不同。排查只能靠基线对比（升级前后的 tok/s 与评测分数）。这也解释了为什么第23课把"默认值 diff"排在九问第 2 位——静默失效只能靠流程发现，不能靠报错发现。

C7（设计题-三镜像）

流转接口点与检测：

  1. 量化产物 → 推理加载：compressed-tensors 格式版本必须匹配（0.20.1 双向）。检测：加载时读 config.json 的 quantization_config，与推理镜像的 compressed_tensors.__version__ 对比，不匹配就 fail-fast。
  2. 训练产物 → 量化输入：TRL 保存的 PEFT adapter 若挂了 lm_head（fused LM head 默认开启），量化工具可能不认。检测：量化前跑一次 peft 加载 + 前向，验证 adapter 生效。
  3. tokenizer 一致性：transformers 5.x 重构了 tokenizer（四后端），不同 minor 间 chat_template 渲染可能有差异。检测：三个镜像各跑一遍同一组 prompt 的 apply_chat_template，输出必须逐字节相同。
