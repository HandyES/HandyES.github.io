二、本课对"企业级智能研究助手Agent系统"的贡献

第22课是收官课，毕业答卷已经交付。但架构文档不会因为课程结束而保鲜：毕业答卷里那张"推理集群配置表"写下的每一个参数默认值，都可能在这两个月里被上游改掉。本课做的就是"给已交付的架构做一次带证据的回归"。

本课产出三个项目资产：

  1. 引擎升级检查表 v1——九问九答，把"能不能升"从经验判断变成可执行清单（§8.3），直接进毕业答卷附录
  2. KV 预算重算器 v2——在原第19课公式上增加"精度档位"轴，输出每种 KV dtype 下的并发容量与代价（§9 脚本A）
  3. 容量模型修订件——三约束模型（显存／解码带宽／Prefill 算力）之外补上第四项"形态切换成本"，用于评估 PD 分离是否值得（§6.5、§9 脚本C）

一个反直觉的收获：本课最大的发现不是"出了什么新功能"，而是基线本身就不准。第19课记的 vLLM v0.28.0 / SGLang v0.5.18 在 2026-09-13 当天已经不是最新——两家分别已在 09-09 和 09-05 各发了一个 minor。也就是说"两个月"实际跨的是 4 个 minor，而不是 2 个。这件事写进方法论比写进结论更有价值。

三、开篇：你背下的那套参数，默认值已经换过两轮了

先做一个小测。第19课你写下的部署命令里，这几个参数各自是什么含义？

三个月后，其中至少三项的"默认值语义"被上游改动了：max_num_batched_tokens 的默认值在更早的版本已从 8192 改成 16384；max_tokens 不再从上下文窗口里预留；KV Cache 的默认 dtype 在某些卡上已经不是你写的 fp16。也就是说，即使你一个字都没改，你的服务行为也已经变了。

这就是"快照型知识"的宿命：它有用，但它有保质期，而且保质期比你以为的短。本课要教的是三件事：

  1. 怎么判断一份快照过期了（§4.1）
  2. 过期之后先看什么（§5–§7，按"架构影响面"排序，而不是按版本号排序）
  3. 怎么把"升级"从一次冒险变成一次流程（§8）

一个判断标准先给出来，后面反复用：

只有改变了默认值、改变了数据布局、改变了失败模式的变更，才需要改架构文档。 新增一个端点、多一个 flag、涨一点吞吐，属于"读到就行"；默认值翻转、KV 落到主机内存、PD 实例可运行时切换——这三类才动你的容量模型。

四、先把基线修对（必须掌握，10min）

4.1 快照当天就可能已经落后

我们对 2026-09-13 那份快照做了反向核查，结论如下：

项目 快照记录的版本 快照当日实际最新 差异
vLLM v0.28.0 v0.29.0（2026-09-09 发布） 落后 1 个 minor，4 天
SGLang v0.5.18 v0.5.19（2026-09-05 发布） 落后 1 个 minor，8 天
TGI v3.3.7（已归档） v3.3.7 一致（但归档发生在基线前约半年）
TRL v1.11.0，并称"下一真实版本 v1.13.0" v1.13.0 已于 2026-09-10 发布 表述在写下 3 天后即失效
transformers v5.15.x v5.17.0 已于 2026-09-09 发布 落后 1 个 minor

这不是笔误，是结构性偏差：写快照的人查的是"我打开页面那一刻的最新 tag"，而 release 的发布时刻、文档更新时刻、tag 创建时刻三者不同步。所以校准的第一条纪律是：

记录 published_at，而不是 tag 名或 README 里的版本号；并且记录你查询的时刻。

4.2 三种核查口径及其盲区

口径 拿到的字段 盲区
GitHub Releases API published_at、tag_name、commit 数 只覆盖"发了 release"的变更；日常合并进 main 的功能看不到；rc 与正式版混杂
PyPI JSON API upload_time、requires_python 只有"能 pip 装"的包；镜像仓库的部分包（如 xformers 某些轮子）时间戳异常
官方 changelog／release notes 语义描述、breaking change 标注 最准确但最慢；不同项目标注习惯差异极大（有的项目把 breaking 写在段首，有的埋在 PR 列表）

本课所有数字都注明来源口径。凡三方口径冲突，以 published_at 为准，并在文中写明——这就是为什么下面每个版本号后面都跟一个日期。

4.3 两个月的真实距离

引擎 窗口内发布 合计产出 平均节奏
vLLM 0.30.0（09-22，762 commits/315 人）、0.31.0（10-05，717/307）、0.32.0（10-18，814/363）、0.33.0（11-01，927/389） 3220 commits，443 位新贡献者 13.3 天 / minor
SGLang 0.5.20（09-18，713 PRs）、0.5.21（10-02，779）、0.5.22（10-19，950）、0.5.23（11-02，1007） 3449 个 PR 15 天 / minor

把这两个数字放在一起看，会得到一个对教学有意义的结论：在推理引擎这个层，"跟版本"是不可能完成的任务，"跟能力线"才是可行策略。 所以本课后面全部按能力线组织（KV／PD／API／破坏性变更），而不是按版本号组织。

4.4 TGI 的"零变化"也是一条信息

TGI 最新 release 仍是 v3.3.7（published 2025-12-19），仓库 archived: true、pushed_at: 2026-03-21。也就是说，它在第19课基线之前约半年就已经停摆，本窗口内零事件。

教学上这条要保留，因为它和第19课"单一厂商引擎的生态风险"是同一个论点的两个证据：一个引擎从"维护模式"到"归档只读"只用了三个月，而迁移成本要在架构期就付。

五、KV Cache 的三次位移（必须掌握，15min）

这是本期影响架构文档最深的一组变更。三次位移的共同方向是：KV 不再是"显存里的一块"，而是"内存层级里的一条流"。

5.1 第一次位移：从视存到主机（HiSparse 产品化）

  • 09-22 v0.30.0 引入 HiSparse host-resident 层：sparse-MLA decode 的 KV 页在显存不足时溢出到 pinned host memory，通过 HiSparseConnector 启用，并补了 Prometheus 计数、TP rank 之间共享 host cache。
  • 10-19 SGLang v0.5.22 让 HiSparse 支持 EAGLE 与 MTP（投机解码路径也能吃到分层 KV）。
  • 11-02 SGLang v0.5.23 让 MLA decode context parallelism 把前缀缓存留在 HiCache 的 file-based L3。

架构含义：第20课的"三约束容量模型"里，显存那个约束不再是一个硬墙，而是一条"显存—主机—文件"的软化斜坡。代价是延迟抖动：溢出一次就是一次 PCIe 往返。所以容量模型需要新增一个参数：可接受的 P99 劣化预算，而不是简单的"能放下多少并发"。

5.2 第二次位移：低精度 KV 的默认值翻转

这是本期最需要改文档的一条：

  • 10-18 v0.32.0：NVFP4 KV cache 铺到 SM8x / SM12x 与 SM90。
  • 10-18 v0.32.0：GLM-5.x 在 SM100 上默认使用 FP8 KV cache。官方口径：每 rank KV 显存减半，代价是 TTFT +7~11%，换来吞吐 +2.3~5.5%。
  • 11-01 v0.33.0：ROCm 侧 ROCM_OCTAVE 支持 3-4bit KV，在 RX 7900 XTX 上 KV token 容量是 fp16 的 4.6 倍。

把第19课的公式拿出来，加一个"精度档位"轴：

$$ M_{token} = 2 \times L \times H_{kv} \times d_{head} \times b_{kv} $$

其中 $b_{kv}$ 是 KV 每元素的字节数，以前大家默认 $b_{kv}=2$（fp16），所以把公式教成"×2"。现在这个 ×2 只是三个档位之一：

KV dtype $b_{kv}$ 相对 fp16 容量 典型代价
FP16 / BF16 2 1.0× 基线
FP8（E4M3） 1 2.0× GLM-5.x 在 SM100 上 TTFT +7~11%
NVFP4 0.5 4.0×（理论） 依赖 SM8x/SM12x/SM90 支持
ROCm OCTAVE 3-4bit ~0.5 4.6×（实测，RX 7900 XTX） 仅 ROCm 路径

关键点（考试常错）：容量翻倍不等于吞吐翻倍。GLM-5.x 的实测是"显存减半、吞吐 +2.3~5.5%、TTFT 变差"。原因很简单——KV 变小只缓解了显存约束与 decode 的带宽约束，但 prefill 仍然是算力约束，而且低精度反量化有额外开销。约束模型里，三条约束是并联的，放松一条只取最小值中的那条。

六、PD 分离：从部署拓扑变成调度原语（必须掌握，15min）

第19课讲 PD 分离时，它是一个部署形态：你决定"这两台机器一台做 prefill、一台做 decode"，然后拓扑固定。本期它变成了运行时可变的调度原语。

6.1 运行时切换（这是范式变化，不是功能增强）

10-02 SGLang v0.5.21：PD 实例可以在 prefill / decode 之间运行时切换，不需要重启。

含义链条：

这是本课最重要的架构结论之一。当"形态"变成可调参数，架构文档里那张"P:D = 1:2"的表格就不再是设计，而是策略的初始值。

6.2 一条会踩的默认值变更：延迟释放

10-02 SGLang v0.5.21：PD decode 的 KV 释放默认改成"延迟释放"——等所有 prefill rank 确认（ack）后才释放，超时 30s，可用 SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE_TIMEOUT 调整。

为什么这是"会踩"的变更：

  1. 它改动了一个资源生命周期，不是加了一个功能。升级后你的 KV 显存曲线会整体上移（释放变慢）。
  2. 30s 的默认值是从"最长 prefill 延迟"推出来的经验值。如果你的最长 prompt 的 prefill 尾延迟超过 30s，就会出现"还没 ack 就超时释放"→ 极端情况下 decode 拿到被复用的 KV。
  3. 它是一个默认开的行为，不做任何配置就会生效。

教学结论：升级前必须做"默认值 diff"，这项检查在 §8.3 的九问里排第 2 位。

6.3 llm-d v1.0.0：把 P/D 副本抽象成一个逻辑单元

10-20 发布 llm-d v1.0.0，核心新抽象 DisaggregatedSet：把 prefill / decode 副本当成一个逻辑单元来做协同滚动升级，readiness 以 Pod 快照为准；router config API 升到 v1；全部组件一次性对齐到 v1.0.0。

硬性版本下限：PD 指南需要 LeaderWorkerSet ≥ v0.11.1 且开启 enableDisaggregatedSet。官方原话是"几乎所有的指南在没有 v0.11.1+ 时会坏掉"。

这类"框架级硬下限"是第20课没讲透的一类风险：你的 K8s 编排层版本会变成推理能力的上限。写进检查表。

6.4 Dynamo 的路线：按模型 pin 引擎

Dynamo 走的是另一条路：v1.6.1（10-27）、v1.6.2（11-05），同时额外发"按模型 pin 引擎 digest"的快照分支——10-24 MiniMax-M3.1、11-05 DeepSeek-V4.1-Flash、11-06 Kimi-K3.1-Pro。

含义：Dynamo 承认"引擎发版节奏"和"模型上新节奏"不同步，所以自己维护兼容矩阵，不等上游。这是平台层对第4.3节那个"13.3 天一个 minor"的工程回应。

6.5 三约束容量模型的修订件

原模型（第20课）：

$$ C = \min\left(\underbrace{C_{mem}}{\text{显存}},\ \underbrace{C{bw}}{\text{解码带宽}},\ \underbrace{C{flops}}_{\text{Prefill 算力}}\right) $$

修订后加第四项——形态切换成本：

$$ C' = \min\left(C_{mem},\ C_{bw},\ C_{flops}\right) \times \eta_{switch} $$

其中 $\eta_{switch}$ 是"切换/释放语义带来的有效容量折损"：

$$ \eta_{switch} = \frac{T_{steady}}{T_{steady} + T_{switch} + T_{drain}} $$

  • $T_{steady}$：稳态服务时长
  • $T_{switch}$：一次 P↔D 切换的耗时（0 表示拓扑固定）
  • $T_{drain}$：延迟释放引入的 KV 占用滞留时间（默认上限 30s）

用法：如果你的流量是"白天 decode 多、夜里 prefill 批量跑"，那切换一次可以摊薄几千秒，$\eta_{switch}\approx 1$，PD 动态切换稳赚；如果你的流量是"每 5 分钟换一次形状"，$\eta_{switch}$ 会掉到 0.5 以下，那就老老实实固定拓扑。§9 脚本C 就是这个式子的可运行版。

七、API 层的两家收敛（应当理解，5min）

同一窗口里，vLLM 和 SGLang 各自上线了"把模型当分类器/打分器"的端点。这种"独立收敛"通常意味着一个更深的需求变化。

端点 出现版本 语义 默认
POST /v1/systemone vLLM v0.32.0（10-18） choice / noul / score 三类 默认开启
/v1/decisions vLLM v0.33.0（11-01） OpenAI 兼容的决策端点 默认开启
/v1/decisions、/v1/score SGLang v0.5.21（10-02） 同上 开启

为什么"两家不约而同"值得写进架构课：

  1. 推理引擎开始承担"判别"职责。以前判分/分类要你另起一个小模型服务；现在引擎内建。这直接压缩了第21课"学习信号管道"里"评审模型"的部署成本。
  2. 它把"生成"和"判定"放到了同一个 GPU 池。这是好事（池化、复用 KV、统一观测）也是坏事（判分流量会和生成流量抢资源，优先级隔离要重做）。
  3. /v1/score 与 /v1/decisions 的"默认开启"意味着暴露面变大。安全评审要重新过一遍端点清单——这是第8节第 7 问的来源。

另外两条工程侧变化：SGLang 从 10-02 起前缀缓存默认跑 Rust core（不支持时自动回落 Python）；vLLM 0.32.0 的 --api-server-count > 1 会把连接路由到最空闲的 API worker，短请求 req/s 提升 43–85%。

八、升级风险清单（必须掌握，15min）

九、引导式代码实践（三层结构）

三个脚本全部纯标准库、纯 CPU、秒级可跑，把本课的三个结论做成可执行的数字。

9.1 第一层：完整可运行代码

脚本A：kv_budget_v2.py——带精度档位的 KV 预算重算器

预期输出：

读数：8B 单 token KV = 2×32×8×128×2 = 131,072 B = 128 KB，与第19课手算的 192KB（那次用 48 层/8 头）不同——层数变了，KV 就变了，别背数字，背公式。fp16→fp8 容量正好 2×、fp8→nvfp4 再 2×，这是因为公式对 $b$ 是线性的。但记住 §5.2 的教训：容量翻倍≠吞吐翻倍，本例只算容量上界，真实并发还要被 C_bw 与 C_flops 压回来。

脚本B：upgrade_scan.py——release notes 关键词扫描器

把"九问"变成规则表，对任意文本做风险标注（不需要联网，把 changelog 粘进字符串即可）。

预期输出：

读数：注意 P2-新增 那一行虽然被标成最低优先级，但它里面藏着 enabled by default——规则扫描只能做初筛，人必须把每条 P2 再看一眼。这正是本课反复强调的"默认值优先于功能"。

脚本C：pd_switch_econ.py——形态切换的经济性

预期输出：

读数：30s 的延迟释放默认值，在"每15分钟换形状"的场景里直接吃掉 2.9% 的有效容量（0.952→0.923）；换形状越频繁，折损越陡。这就是 §6.2 说的"资源生命周期变更"的量化后果——它不是正确性问题，是账本问题。

9.2 第二层：改一个参数看结论怎么变

把脚本C 的 drain 从 30 改成 5（也就是把 SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE_TIMEOUT 调到 5s）：

  • 若你的最长 prefill 尾延迟 < 5s，安全，$\eta$ 回到 0.95 附近；
  • 若最长 prefill 尾延迟有 20s，则 5s 会频繁超时——风险曲线是阶跃的，不是渐变的。这就是为什么这个参数不能"拍一个小一点的值"。

9.3 第三层：可选拓展（非教学必需）

  • 用真实 vllm bench serve 在你自己的负载上复测 fp16 与 fp8 KV 的 TTFT 差异，验证 §5.2 那个 +7~11% 是否在你的模型上成立；
  • 把脚本B 接到 gh api releases 的输出上，做成每周一次的自动风险简报（注意本机环境需处理 TLS，见第12节）。

十一、参考答案

A1（基础-公式）

$M_{token} = 2 \times L \times H_{kv} \times d_{head} \times b_{kv}$。$b_{kv}=2$ 为 FP16/BF16（1.0×），$b_{kv}=1$ 为 FP8/E4M3（2.0×），$b_{kv}=0.5$ 为 NVFP4（理论 4.0×；ROCm OCTAVE 实测 4.6×）。常见错误：用注意力头数而非 KV 头数；漏掉 ×2（K 与 V）。

A2（基础-约束）

因为容量模型是 $\min$ 而不是求和。KV 变小只放松 $C_{mem}$（以及部分 $C_{bw}$），如果此时瓶颈已转移到 $C_{flops}$（prefill 算力），那放开的显存只换来"能排队更长"，不换来吞吐。GLM-5.x 的实测正是：显存减半、TTFT 变差 +7~11%、吞吐只 +2.3~5.5%。

A3（基础-llm-d）

解决"P/D 副本作为两个独立 Deployment 时，滚动升级会短暂出现版本错配、readiness 判断失真、路由打到半就绪副本"。DisaggregatedSet 把它们抽象成一个逻辑单元，升级与就绪判断都在单元级完成。硬性要求 LWS ≥ v0.11.1 是因为该抽象依赖 LeaderWorkerSet 的组语义（组内有序创建/就绪）。

B4（分析-破坏性变更）

  • 长 prompt 400 → max_tokens 不再从上下文窗口预留（0.32.0）
  • 跨域全挂 → 默认 CORS 不再放行任意 origin（0.32.0）
  • 投机解码配置不生效 → Medusa 与 MLP speculator 被删除（0.33.0）

这三条正好覆盖"参数语义、安全默认、能力删除"三类，是 §8 分类的实例。加分项：指出这类问题在灰度环境里都测不出来——除非灰度环境用的镜像 tag、CORS 配置、投机解码配置与生产一致。

B5（分析-PD 经济性）

稳态时长按"一个形态连续服务多久"算：白天 10 小时 = 36,000s，夜间批量 4 小时 = 14,400s，一天切换 2 次，每次 45s，$T_{drain}$ 取 30s：

$\eta = 36000/(36000+45+30) \approx 0.998$，夜间 $\eta \approx 0.995$。

结论：稳赚，开。 但要注意两点：①切换窗口内要有"在途请求"处理策略（否则那 2 次切换的 1.5 分钟会打出一批超时）；②如果夜间批量的 prompt 极长（>30s prefill 尾延迟），$T_{drain}$ 要调大，$\eta$ 会掉。

B6（分析-默认值）

因为功能是"加法"，默认值是"改法"。加法你不调用就不受影响；改法你不配置就被动接受。本课例子：GLM-5.x 在 SM100 上默认 FP8 KV——你什么都没改，KV 显存减半、TTFT +7~11%，SLA 变了。另一个：max_tokens 不再预留——你什么都没改，长 prompt 请求开始 400。

C7（设计题-参考方案）

①灰度环境：镜像 tag 与生产完全一致（避免 -cu12x 类 lane 差异），GPU 架构一致（SM90 与 SM100 的默认 KV dtype 不同），K8s 与 LWS 版本一致（LWS ≥ 0.11.1）。

②流量切分：按 prompt 长度分层（<2K / 2K-8K / >8K）各取 10%，因为 max_tokens 语义变更只打在长 prompt 上；再叠一层按请求类型（生成 / 工具调用 / 判分），因为新端点的默认开启影响判分流量。

③回滚阈值（观察窗口 30min）：错误率 >1%（基线 0.2%）；P99 TTFT 劣化 >20%；OOM 次数 >0；KV 显存曲线较基线抬升 >15%（这条专抓"延迟释放"类变更）。

④CI 接入：把 §8.4 九问做成 PR 模板 + 脚本B 的规则扫描；发布前一天自动拉 gh api releases 生成风险简报；P0 项未勾选禁止合入。
