二、本课对"企业级智能研究助手Agent系统"的贡献

前两课修的是"能被 pip list 查出来的东西"——引擎版本、权重量化。本课修的是查不出但更要命的东西：

  • 版本命令显示 langgraph 1.2.20，和两个月前的 1.2.x 看不出区别，但 DeltaChannel 的默认快照间隔从 1000 变成了 100；
  • MCP 协议号还是 2026-07-28，一个字没变，但升级 Python SDK 后你的工具注册表可能直接 import 失败；
  • A2A 的仓库还在，代码还能跑，但治理表述少了一层：A2A 现在挂在 Linux 基金会旗下的 AAIF 上，而你的文档只写到"Linux 基金会"。

本课产出三个项目资产：

  1. 协议升级守卫脚本——把 MCP SDK v2.3.0 的注解约束做成 import 前的静态扫描（§9.1 脚本A）
  2. 评测可信度体检表——κ 与增益归因两张表，进第17/20课的评估体系（§8）
  3. Context 管道指标定义——"损耗率 / 字段到达率 / 有效利用率"三个指标，补进第4课 Context Engineering（§7.1）

本课与前三课最不一样的一点：第23/24课的错误可以靠 git diff 版本线发现，本课的错误没有版本线可查。A2A 的治理结构加层不发 release、MCP 协议号不动、langgraph 的 minor 里藏默认值变化。所以本课要建立的不是"跟版本"的习惯，而是"跟语义"的习惯。

三、开篇：三种"过时"，难度递增

把前两课和本课放在一起看，过时其实分三种：

类型 例子 发现方式 难度
①版本落后 vLLM 0.28.0 → 0.33.0 查 release notes 低
②默认值/工具迁移 AutoAWQ → llm-compressor 读文档 + 实测 中
③语义漂移 A2A 治理结构加层（AAIF）、SDK 注解收紧、默认快照间隔 没有 release 可直接查 高

第③类为什么难：它通常藏在"看起来没变"的地方。版本号没动，changelog 里可能只有一行 DeltaChannel default snapshot interval 1000 -> 100；治理方变更发生在基金会的新闻稿里，不在代码仓库；SDK 的注解收紧写在 migration guide 的一个脚注里。

所以本课的方法论是：按"决策"而不是按"仓库"来核查。

先给一个贯穿全课的判断标准：

当"协议号/主版本号"没变时，恰恰是最该去查 minor 与 SDK 的时候——因为大版本不动，意味着变化都被塞进了默认行为和实现细节里。

四、先把基线修对：三处旧文纠错（必须掌握，10min）

这一节的共同点：三处都不是"作者查错了版本"，而是作者查的是对的、但信息在快照之后被语义层改写了。

4.1 纠错①：A2A 的治理表述该补一层——AAIF

旧文（00-教学大纲.md、0014、0015 多处）写的是 "A2A 在 Linux 基金会治理下"。

这句话没有说错。它缺的是中间一层。核实到的一手事实如下：

时间 事件 一手来源
2025-04 Google 发起 A2A，并捐赠给 Linux 基金会 a2a-protocol.org 首页 Governance 段
2026-03 A2A v1.0 稳定规范发布（旧文写"2026年初"，可细化为 3 月） a2a-protocol.org 博客
2026-08-17 AAIF 官方博客宣布 A2A 作为 hosted project 加入 aaif.io/blog/a2a-joins-aaif
2026-08-27 A2A 官方博客宣布被接纳为 AAIF Growth Stage 项目 a2a-protocol.org 博客

判断的关键就在这两篇博客的措辞里：

  • A2A 官方博客：accepted as a Growth Stage project at the Agentic AI Foundation (AAIF)，同时写明是 operating under the Linux Foundation-directed AAIF；
  • AAIF 官方博客：The Agentic AI Foundation, hosted by the Linux Foundation, provides that structure.

也就是说：AAIF 本身是 Linux 基金会托管、主导的基金会，A2A 是它的 Growth Stage 项目，与 MCP、goose、AGENTS.md、agentgateway 同在一个栈里。所以"Linux 基金会治理"作为伞层表述依然成立，要补的是中间这一层——现在准确的说法是：

A2A 是 Linux 基金会旗下 AAIF 的 Growth Stage 项目，与 MCP 同栈。

为什么这条仍然值得讲，哪怕只是"补一层"：

  • 治理粒度决定风险粒度。伞层（LF）管法律实体与 IPR，子基金会（AAIF）管规范投票席位与技术路线。写架构文档时问"谁在定这个协议"，答案要能落到 AAIF 这一层——因为它同时托管 MCP，两个协议的演进开始共享同一套治理节奏。
  • "同栈"比"同基金会"更有信息量。A2A 与 MCP 现在同属 AAIF 栈，意味着互操作问题（Agent↔工具 与 Agent↔Agent 的边界、身份、网关）会被放进同一个治理盘子里讨论，而不是两个互不相干的社区各推一套。
  • 这条恰好是"二手转述会骗人"的活样本。多处二手摘要把这件事写成"A2A 退出 Linux 基金会 / 换了东家"，属于过度 claim：一阶事实是"加入了 AAIF"，二阶结论"不再属于 LF"被一手页面直接否定。校准必须回到一手来源——这是 §8 评测可信度那套纪律在"事实核查"上的同构版本。

4.2 纠错②：MCP 协议没升版，破坏性在 SDK

旧文把 MCP 的更新写成"协议修订版推进"。事实：

  • MCP current 仍是 2026-07-28，窗口内没有新的协议修订版。
  • 真正的破坏性变更在 Python SDK v2.3.0（2026-10-02）（下一节详述）。
  • 官方 Ruby SDK 于 10-30 升为 Tier 1——这是 SDK 生态成熟度事件，不是协议事件。

这个纠错的教学价值最大："协议版本"和"SDK 版本"是两条独立的线。协议是规范（spec），SDK 是实现。规范不动、实现破坏性升级，是 MCP 生态这一期的真实形态。如果你只盯 spec 版本号，会完全漏掉这次升级。

4.3 纠错③：langgraph 1.3 / 2.0 是传闻

旧文及部分社区讨论里出现 "langgraph 1.3 / 2.0" 的说法。事实：主线仍是 1.2 系列，最新 1.2.20（2026-11-05）。1.3 / 2.0 未发生，属传闻。

窗口内 langgraph 的真实变化（都在 minor 里）：

版本 日期 变化
1.2.19 2026-10-30 DeltaChannel 默认快照间隔 1000 → 100
1.2.20 2026-11-05 每个 task 内 interrupt() 有独立 id、支持 strict resume

第 1 行是最典型的"③语义漂移"：一个默认值从 1000 变 100，意味着状态快照频率提高 10 倍——长会话的检查点数量、存储写放大、resume 速度全都变了，而 pip show langgraph 只会告诉你 1.2.19。

4.4 三处纠错的共同教训

把三处并排，可以看到一条规律：

纠错 表层信号 真实变化所在层
①A2A 无 release 治理/组织层
②MCP spec 号不动 SDK 实现层
③langgraph 主版本不动 默认值层

规律：越是"看起来没变"的层，越可能藏着需要改架构文档的变化。 因此校准清单不能只有"版本 diff"，必须有"组织层 / 实现层 / 默认值层"三个额外检查项。

五、协议层：MCP 的"注册即抛"与 A2A 的演进（必须掌握，15min）

5.1 MCP Python SDK v2.3.0 的四个破坏性变更

这是本课最需要动手验证的一节。四个变化：

变更 具体行为 影响面
硬依赖 httpx2>=2.10.0 + 新增 max_sse_event_size 传输层依赖升级 依赖解析、SSE 大事件上限
x-mcp-header 注解校验收紧 工具注册时，带非法注解直接抛 InvalidSignature import 期失败，不是运行期
空 _meta 与空 params 不再发送 wire 格式瘦身 依赖空对象的对端解析
ctx.meta 由 {} 变 None 上下文对象语义变化 ctx.meta.get(...) 会 AttributeError

第二条要展开讲。SDK 现在只接受 plain str / int / bool 作为 x-mcp-header 注解类型，以下全部拒绝：

  • str | None（Optional 联合）——要用 str + 默认值表达"可缺省"
  • float——改传 int 倍率
  • list / enum——列表放 body、枚举传 str 字面量

为什么是 InvalidSignature：MCP 的工具 schema 要跨进程/跨语言传输，header 注解必须能被无歧义地序列化成 wire 类型。联合类型、浮点、容器、枚举在不同语言 SDK 里映射不一致，所以 v2.3.0 选择在注册边界就拒绝，而不是在运行时静默降级。

这个设计决策本身值得记一笔："在边界处尽早失败"优于"在内部尽力兼容"——和第24课 VLLM_MARLIN_INPUT_DTYPE 删除（静默失效）恰好是反面教材。同一个生态里，两种错误哲学都有，所以不能靠"框架会帮我兜住"。

6.2 OpenAI Agents SDK：alpha 里的一次全改名

稳定版 0.24.0（10-15）只是小步。真正的大改在 0.24.0-alpha.6（11-03，仅 GitHub Releases，带 native runtime wheel，支持 CPython 3.10–3.14）——几乎把面向用户的 API 全重命名了：

旧 新
Runner.run(...) Agent.run()
Turn.wait() get_result()
Session.interrupt() Turn.cancel()
Subagent.submit() start()

外加：Agent 声明改为不可变、新增 NativeOutput / SessionState / NetworkPolicy / agents.testing.ScriptedResponses。

教学含义（比改名本身更重要）：这是一次从"过程式 Runner 驱动"到"以 Agent 为中心的对象模型"的迁移。Runner.run(agent, ...) 是"我拿一个执行器去跑一个 agent"，Agent.run() 是"agent 自己跑"。加上"Agent 声明不可变"和 SessionState 单独抽出，方向很清楚：状态与身份分离、执行权下沉到对象。

要不要跟？给一条判断：alpha 且仅 GitHub Releases（未上 PyPI）→ 不进生产，但进"下一版架构预研"。因为这次改名不是修补，是模型变更，等它 GA 时你的编排层要重写一遍；提前把"Runner 驱动"的代码隔离在一个适配层里，迁移成本能压到最低。

7.1 Context 是管道，不是窗口（最重要的一条）

Context Is a Pipeline, Not a Window（arXiv 2610.36114，10-26）在 720 次运行里测到：

  1. 显式状态表 > 向量检索。第8课"记忆用向量库"的默认要改成"结构化状态优先，检索为辅"。

7.3 多 Agent：把"角色分工"降级为"反馈回路"

2611.03931 是本期对第13课冲击最大的一篇：

  • 固定预算下删掉角色分工，几乎不损首答准确率；
  • 同等反馈次数下，有无角色的差异仅 +0.009（95% CI −0.014 ~ +0.033，跨 0，即不显著）；
  • 但强制每轮提交使恢复率从 0.198 → 0.613（3.1×）。

结论很刺眼：多 Agent 的收益主要来自"反馈与恢复回路"，不是"谁扮演产品经理、谁扮演工程师"。再加两条佐证：

  • 2611.07140：多数投票只挡住最弱的那一个（不是普遍提升）；
  • 2610.32060：3,211 条失败轨迹集中在恢复/纠错与共识，不是角色定义不清；
  • 2610.40758 (CLR-Bench)：自演化最强仅 +5 点，排除未见成员后只剩 6–12%；而一条固定规则提示反而 +14.5~16.5 点——手写规则打赢了自演化；
  • 2611.01415 (Latent Harness)：rank-8、0.03–0.05% 参数即可，同容量 LoRA 需要 11.1× 参数量；
  • 2611.03868 (EvoGroup)：EverMemBench 71.07% → 89.58%（正面的记忆自组织案例）。

→ 改课建议②：第13课多 Agent 架构，把"角色分工"从核心设计降级为可选的表达层；把"强制提交点 / 反馈回路 / 恢复协议"升为核心。第20课评估体系里，"有几个角色"不再算复杂度收益，"每轮是否有可恢复的检查点"才算。

7.4 Agentic RL：先 SFT，RLVR 买的是分布外鲁棒

2611.07639（预注册研究）给出一条非常干净的成本-收益曲线：

配置 hard split 同分布 OOD
SFT 1,200 条 0.785 — —
15 步 GRPO 0.314 — —
base 0.311 — —
60 步 GRPO — +0.22 点 +0.33
总成本 — — $8.69

读法：SFT 1,200 条在 hard split 上把 GRPO 甩开一倍多（0.785 vs 0.314）；RLVR 在同分布上只有 +0.22 点，在 OOD 上 +0.33 点。所以结论不是"RL 比 SFT 强"，而是：先把 SFT 做够，RLVR 主要买的是分布外鲁棒性，不是同分布涨点。

这直接修正第17课的路线：预算有限时，先堆高质量 SFT 数据，再上 GRPO，而不是反过来。

两条配套警告：

  • 2611.02574：GSM8K 58.0→61.3、Pass@256 94.5→96.9，但错误探测 probe 的 AUROC 全程 0.798–0.840 不变 → 模型答得更好了，但它并不更"知道自己错了"。所以别把 RL 后的准确率当成"可自我校验"的证据。
  • 2611.03260：不匹配数据带来 1/μ² 噪声放大 → 数据配比在 RL 阶段比 SFT 阶段更敏感。

7.5 生产与 Computer Use：世界会变，Agent 看不见

  • 2610.39282：完全加载的页面上 0.4% 点击 30s 内变陈旧；首秒内规划的点击 17% 变陈旧；10 个开源 agent 里 8 个等待规则仍留 >1% 陈旧点击。
  • 2610.40246 (EnvOS)：任务中途世界改变时，自发察觉 0/16；被提醒复查 2/16；直接把新值显示出来 15/16（p=0.00293）。
  • 2610.27645 (CUA-Recovery)：Error Awareness Rate ≤44.0%、Pass@3 ≤25.5%。
  • 2611.02543：SGLang 上 10 分钟尖峰使随后 1 小时 goodput 降约 88% 且不自动恢复；Basin 在 H200 1P3D 达 Continuum 的 1.20–1.70×。
  • 2610.39230：15 个金融部署、约 11 个月——单 agent 幻觉率 7–9%，多 agent 校验 <1%。

三条架构含义：

  1. EnvOS 的 0/16 是本期最该记住的数字：Agent 不会自己发现世界变了。要显式设计"重观察"触发点，而不是指望模型推理出来。
  2. goodput 降 88% 不自动恢复（呼应第23课容量模型）——尖峰后的降级是粘性的，必须有人为/自动的恢复动作，不能假设"过一会儿就好"。
  3. 多 agent 校验把幻觉 7–9% 压到 <1%，这是 §7.3"角色分工无用"的一个重要例外：校验回路有用，角色标签无用。两者并不矛盾——又一个"要回路不要角色"的证据。

这一节是第③条改课建议的依据，也是整期校准里最"反直觉"的一块。

2611.04090：5 个 judge 重判 4,000 场 Arena，与人类判定级一致的中位 κ = 0.22；排序 Kendall τ 0.17–0.89（跨度极大）。κ=0.22 意味着"轻微一致"——两个 judge 的一致，大部分来自"都倾向给 pass"这个偏斜，而不是判断力相同。§9.2 脚本B 会用构造数据把这一点算出来。

2611.00491 (VoirDire)：改成连续打分，MAE 最多降 26.8%。→ 打分粒度比"换更强的 judge"更划算。

检查项 阈值/动作 依据

十一、参考答案

A1（基础-三处纠错）

①A2A 于 2026-08-27 被 Linux 基金会旗下的 AAIF 接纳为 Growth Stage 项目（原来"Linux 基金会治理"仍成立，缺的是中间层，不是"改换东家"）——变化在治理/组织层；②MCP 协议未升版（current 仍 2026-07-28），破坏性在 Python SDK v2.3.0——变化在实现层；③langgraph 1.3/2.0 是传闻，主线 1.2.20，真实变化是 DeltaChannel 快照间隔 1000→100——变化在默认值层。三者都没有主版本号/reVision 号的变动可查，所以不是"版本落后"，必须靠"组织层 / 实现层 / 默认值层"三个额外检查项才能发现；而第①条还多一层教训：二手摘要的二阶结论比一阶事实更容易错。

A2（基础-注解类型）

只接受 plain str / int / bool。四种被拒写法与替代：str | None → 用 str + 默认值表达可缺省；float → 改传 int 倍率；list → 放进 body；enum → 传 str 字面量。常见错误：以为 float 只是"精度问题"会被自动收窄——不会，注册期直接抛 InvalidSignature，且是 import 期失败而非运行期。

A3（基础-ctx.meta）

None 没有 .get() 方法。最小修复：meta = ctx.meta or {} 后再 meta.get(...)，或显式 if ctx.meta is None: ...。关联：同时要处理"空 params 不再发送"——对端不能有 assert "params" in msg。

B4（分析-快照间隔）

原因是 langgraph 1.2.19 把 DeltaChannel 默认快照间隔从 1000 改成 100，快照频率提高 10×，检查点数量与存储写放大约 10×。这类问题没有版本 diff 可发现，因为：主版本号没动、pip show 只报 1.2.19、变化藏在一个不显眼的默认值里。正确做法是把"默认值 diff"独立成升级检查项（呼应第23课"引擎升级九问"第 2 问），并复用第23课 §5 容量模型重算检查点存储预算。

B5（分析-一致率陷阱）

81.8% 是原始一致率 po，在偏斜分布下会被"双方都倾向打 pass"抬高。脚本B 的构造数据里，pe=76.6%（纯靠猜测分布就能撞对的一致率），扣除后 κ=0.2222，只算"轻微一致"，恰好对应 2611.04090 里 5-judge 中位 κ=0.22。该补报：Cohen/Fleiss κ、混淆矩阵、打分档位数（档位不同 κ 不可比），并按 2610.38076 补做语义等价改写鲁棒性测试。

B6（分析-看似矛盾）

不矛盾，恰好互相印证。2611.03931 否定的是**"角色标签/分工"这一表达层（删掉角色几乎不损首答准确率，有无角色差异 +0.009 且 CI 跨 0）；2610.39230 肯定的是"多 agent 校验回路"这一功能层（幻觉 7–9% → <1%）。同一篇 2611.03931 还给出"强制每轮提交使恢复率 0.198→0.613"，说明真正起作用的是提交点 / 反馈 / 恢复 / 校验**这些回路，不是"谁叫产品经理"。结论：要回路，不要角色——这就是 §7.6 改课建议②。
